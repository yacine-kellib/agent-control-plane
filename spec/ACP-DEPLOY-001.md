## What this document does not do

This section comes first because the limits are larger than the claims, and a reader who
stops here should stop with the right impression.

**Nothing here is executed.** 78 of this document's 85 clauses have no check that
would catch their violation. That is not an oversight to be fixed later by writing more
tests — most of a deployment specification constrains an operator's infrastructure, and this
repository's gates run in a process, not in a datacentre. §9 names every unchecked clause
explicitly rather than leaving the coverage claim to be inferred, because normative text
with no executable consumer is this project's recurring defect: it produced three published
corrections in a single day (the schema describing an artifact nobody builds, AU-1's audit
chain disagreeing with the reference, and `CL-7` naming two normative rules).

**Nothing here runs.** The architecture this document specifies has no implementation. The four Rust
services' `main()` returns `ExitCode::FAILURE` and the two TypeScript services have
no entry point at all (ACP-63), and four components named
throughout — the API gateway, the KMS signing substrate, the audit service and the egress
proxy — have no source directory at all. The one that matters most is the KMS: custody tiers
T2 (cloud KMS) and T3 (HSM) are **declared and not implemented**, T0 refuses to sign for
production and T1 wipes its key after one signature, so **no implemented custody tier can
serve as an online production receipt signer**. A specification for a system that does not
exist is a design document wearing normative clothing, and it should be read as one until
the gate says otherwise.

**Its source was untracked.** This document was derived from
`docs/private/acp-deployment-architecture.html` — a file that is gitignored, unsigned,
outside the ten signed roots, and read by nothing. That the most load-bearing design
artifact in the project lived where no gate and no manifest could see it is itself the
finding that prompted this document.

**It is incomplete, and here is where.** Clause ids **DP-68, DP-69 and DP-70 are not
allocated**: §8 (Backpressure and Capacity) was scoped for six clauses and carries three. The
gap is left visible rather than renumbered away, because renumbering would hide that §8 is
the thinnest section in the document. Section 8 should be read as a stub.

**It has not been adversarially reviewed end to end.** Individual sections were reviewed
against four lenses — clause-id collision, RES-8 self-certification, defaults that change no
outcome, and contradiction with `ACP-SPEC-001` — and 352 defects were raised and largely
applied. The whole-document pass that would ask *what is missing* never ran. Known
candidates it would have raised: clock and time source, certificate and identity lifecycle,
key rotation for the bundle and receipt keys, tenancy isolation, disaster recovery, and
upgrading the control plane while a bundle epoch is live. **None of those are covered here.**

## Relationship to ACP-SPEC-001

`ACP-SPEC-001` is normative for *behaviour*: what the Executor must verify, what fails
closed, what must be recomputed rather than trusted. It is thorough on failure semantics —
idempotency and at-most-once (`DS-1`..`DS-4`, with the Y3 defect mechanized both ways in
Dafny), ledger partition behaviour (`CL-1`..`CL-8`), timeouts and expiry (`DR-9`, `AT-5`,
`M-5`), availability attacks on the approver queue (`AQ-1`..`AQ-3`), and a latency budget
per risk class (`EO-2`) published together with the open conflict that it is exceeded.

This document is normative for *where behaviour runs*: trust-domain isolation, deployment
profiles, key custody binding, datastore guarantees, cold start, degraded mode and
backpressure. It adds no behavioural requirement and **must not restate one** — where a rule
already exists in `ACP-SPEC-001`, this document cites it and does not paraphrase it. Two
descriptions of one rule drift apart, which is the encoding-split defect arriving in the
documents that exist to prevent it.

Clause ids use the `DP-` family, which collides with no family in `ACP-SPEC-001`.

> **Gate note.** `tools/selftest.sh`'s clause-id uniqueness assertion currently scans
> `spec/ACP-SPEC-001.md` by literal path, so **it does not see this file**. Until that check
> iterates `git ls-files 'spec/*.md'`, a `DP-` collision — with itself or with a clause in
> `ACP-SPEC-001` — would ship green. Writing this document without widening that check would
> reproduce `ACP-56` exactly.

## 1. Status of This Document (Normative)

> **⚠ NORMATIVE ALERT (first revision). This document is new, it is unconfirmed, and most of its clauses are checked by no command.** ACP-SPEC-001 §1 records the same defect three times in one revision — normative text with no executable consumer: a bundle schema describing an artifact nobody builds, an audit-chain formula (AU-1) no suite ever compared against, and a clause id (CL-7) naming two different rules. A *deployment* specification is more exposed to that defect than any other kind, because almost nothing it says can be executed: no control-plane service in the reference repository boots — no service has a startable entry point (ACP-63), so a scaffold cannot be mistaken for a running control plane — and no command reads this document's prose. §9 is therefore part of the normative text and not an appendix to it — it names, per clause group, the command that goes red when a clause is violated, or says plainly that none does. A clause here with no entry in §9 is an editing error, not a covered clause.
>
> **The clause ids in this document are, at the time of writing, checked by reading and not by running.** The clause-id uniqueness assertion in `tools/selftest.sh` takes one hardcoded path, `spec/ACP-SPEC-001.md`, and does not see this file; an id here that collides with a live id there ships green. `DP-` was verified free of collision against ACP-SPEC-001's bullet-defined families, against every clause prefix appearing anywhere in `spec/`, `dossier/`, `README.md` and `CLAUDE.md`, and against the whole working tree including gitignored files. That verification is a fact established by reading, and it decays the moment anyone allocates a family. §9 specifies the widening that turns it into a control and states what remains uncovered afterwards.
>
> **No part of this document has had independent adversarial review.** ACP-SPEC-001 §14 suite 11 is not closed for the specification either, and this document inherits that status without adding evidence of its own. Its section list and its clause allocation were not independently reviewed, which matters more here than it usually would: §3 and §4 exist because self-certification is this architecture's recurring failure, and a document arguing that, written and reviewed by one party, is the shape it warns about.

- **DP-1. This document is normative for deployments, and it is not part of Door A Conformance.** Conformance (§14) defines an implementation as **Door A Conformant** iff it satisfies every MUST/MUST NOT in ACP-SPEC-001 §§2–15 and passes the conformance suites §14 enumerates. This document sits outside that range, and publishing it does not move it. Satisfying this document is a separate claim — **ACP-DEPLOY-001 Conformant** — made about a *deployment* rather than about an implementation. Neither claim implies the other, and each **MUST NOT** be represented as the other. Bringing this document inside §14's range is an amendment to ACP-SPEC-001 §14, which increments that document's version under the release-integrity rule in its §1, and **MUST NOT** occur as a side effect of publishing or revising this file.

  *Rationale, and why this is a separate document rather than an expanded §12.* The deciding argument is conformance scope, not length. Had these clauses been added as an expanded Deployment Requirements (§12) or as a new §16, they would have joined §14's surface by section number alone: every implementation already assessed against §§2–15 re-scoped by a document it never saw, and a substantive normative change made through an editorial one. Allocating outside ACP-SPEC-001 has precedent — ACP-CLASS-001 carries the suite-12 classification artifact and allocates the open notifier finding **T-32**, which §9.6 cites; ACP-AUDIT-001 and ACP-REVIEW-002 are likewise separate document ids. The citation graph is already multi-document, and extending §14's range is now an explicit act taken deliberately or not at all.

  *What breaks without it, and the second direction is the worse one.* Without the separation, an implementer is told they are non-conformant for a network boundary they do not control. Worse, a deployment presents "Door A Conformant" as covering its substrate — which a §16 would have made true on paper without anyone testing a host.

  *Checked by.* Nothing. No command compares a conformance claim against the range §14 quantifies over, and none in this repository could: the claim is made in a vendor's prose, not in a file here. §9 carries the register. Naming a claim is not the same as making it checkable, and §9 states which parts of this document are checkable at all — the third bucket there is the largest.

- **DP-2. Where this document and ACP-SPEC-001 disagree, ACP-SPEC-001 governs.** A disagreement is a defect in *this* document, to be corrected here; it is never a variance a deployment may exercise. This document **MUST NOT** relax any MUST or MUST NOT in ACP-SPEC-001, **MUST NOT** narrow the conditions under which one applies, and **MUST NOT** introduce a deployment-time configuration knob for any value the policy bundle signs.

  *The worked example is delivery class (DS-5).* Delivery semantics (DS-5) requires the delivery class per action class to be declared in the bundle and recorded in audit. A deployment-time setting for it — even one defaulting to the bundle's value — moves a security-determining value out of an artifact signed under an offline key held by the security-policy role (PB-1), authored and reviewed by distinct identities (PB-2), and into a file on the host the Executor runs on. The Executor then reads at-most-once or at-least-once from the party it is verifying, which is the RES-8 class at the sixth recurrence ACP-SPEC-001 §1 records (C2 → X1 → Y1 → Z3 → W1 → the v1.3.15 quorum-threshold defect). Delivery class is not a small one to lose: at-least-once against a non-idempotent floor-HIGH target is precisely what DS-4 forbids, and the doubled trade or actuator command is the failure DS-2 prefers a dropped action to.

  *The rule cuts both ways, and it is one rule rather than two.* Values whose home is the signed bundle are configured nowhere else: resource floors (RK-1), reversibility class (RV-1), quorum threshold (PB-6), notice recipients (DR-13), signature suite floor (CR-4), delivery class (DS-5). Values whose home is the verifier's out-of-band configuration — the expected verification key and what the verifier believes about how it is held (§4) — **MUST NOT** be moved into the bundle, the manifest or any message in order to make them configurable. In both directions the value's home is fixed by who must not be permitted to choose it, and moving it in either direction hands the choice to exactly that party.

  *Checked by.* Nothing mechanical. DP-2 is a rule about this document's own text, and the only instrument that reads that text is a reader. One instance of the knob it forbids is foreclosed by the bundle-schema assertion §9 ships — no schema under `spec/schemas/bundle/` may declare a deployment profile — but foreclosing one instance is not covering the class. Nothing checks DP-2 itself.

- **DP-3. Requirements of ACP-SPEC-001 are cited by clause id and never restated.** No clause in this document reproduces a requirement of ACP-SPEC-001 in its own words. Where a deployment obligation depends on one, the citation carries the topic and the id — the Bundle Repository isolation boundary (§9.1.1 step 3, D-3), rendering-path independence (DR-2), ledger sharing across Executors (CL-5) — and this document states only the part it adds.

  *Rationale: the encoding-split defect, and two instances published one paragraph apart.* Two descriptions of one object is the defect ACP-SPEC-001 corrected twice in v1.3.15, both times inside its own normative source. The first was the aftermath of the bundle-signature clause (PB-8): `bundle.schema.json` described the artifact as a tree index with a fixed `classical`/`pq` pair, while PB-8 specifies one value per primitive over a covered set established by a canonical walk — a second description introduced by the revision that fixed the same defect one paragraph away, surviving a full release cycle because nothing read the schemas. The second was the audit chain (AU-1): §11.2 stated a preimage the reference implementation had never produced, and the consequence was not that an implementer fails to match but that **AU-3a does not hold** — a third party implementing the clause literally recomputes a different head on an honest, untampered chain and lands in this system's own critical-alert channel with no attacker present.

  *The specific text a deployment document is most tempted to paraphrase.* The Bundle Repository isolation boundary (§9.1.1 step 3) reads like deployment guidance: stronger than filesystem permissions on a host shared with the Policy Engine, separate host, separate credential domain, or hardware-enforced. It is the sentence a topology section most wants to expand into named substrate, and expanding it produces a second normative statement of one boundary, in the document a platform engineer opens first. Note that Deployment Requirements (§12) declines to expand it: D-3 is one sentence that defers. The temptation is strongest and the drift least visible exactly here, because the reader who most needs the boundary is the one least likely to open §9.1.1.

  *This has already happened once, in the artifact this document replaces.* The deployment topology this repository carried before this document was an unsigned, gitignored HTML diagram — outside the signed roots, invisible to the signer, to `tools/sync-counts.sh` and to the clause-id check. It labelled the Bundle Repository "verified on every read (PB-8)". PB-8 specifies the SIGNATURE file's contents and says nothing about per-read verification; verify-on-every-read is real, and it is a property of the implementation (`reference/src/acp_bundle.py`), not of any clause. That is the CL-7 defect inverted — not one id naming two rules, but one rule borrowing an id that does not carry it — and a reader who checks the citation either implements a rule PB-8 does not contain or skips one believing PB-8 covers it.

  *Checked by.* Partially, and only after the widening §9 specifies. A widened clause-id uniqueness check reports an id **defined** twice across `spec/*.md`. Nothing reports an id **cited** for a rule it does not carry, and nothing detects a paraphrase at all — a restatement that drifts is well-formed markdown with a real clause id in it. DP-3's central obligation is unchecked and remains unchecked after every check in §9 has run.

- **DP-4. No numeric bound from ACP-SPEC-001 and no count derived from the repository is reproduced here.** Every limit, window, interval, threshold and rate in Limits and Constraints (§13) and in the evaluation-order latency budget (EO-2) is cited by id; the figure is read from ACP-SPEC-001. Counts derived from the reference repository — files under the signed manifest, suites in the gate, assertions in the self-test — are not published in this document at all.

  *Rationale, and the evidence is already inside the normative source.* As of ACP-SPEC-001 v1.3.15, the end-to-end latency bound exists in three normative places and two of them are stale. EO-2 was revised in v1.3.10 into a per-risk-class budget; §13's `L-10` row still carries a single figure with no risk class, and §9.7's performance note still directs deployments to re-measure against a flat end-to-end warm bound. Both predate the revision that split them. An implementation obeying `L-10` literally raises an SLO breach on a floor-HIGH path EO-2 explicitly permits — or engineers latency out of a path that has already waited on a human quorum and a hold window, which EO-2's own rationale calls a category error. Three statements of one bound; the revision moved one. **This is a defect in ACP-SPEC-001, recorded here and deliberately not corrected here**: correcting it edits the normative source and increments its version, which is a separate release event.

  *And nothing would have gone red.* `tools/sync-counts.sh` re-derives every published **count** and rewrites it across the README, `CLAUDE.md`, the gate script and the dossier. It derives no **limit**, and it writes nothing under `spec/` by design. So a bound that moves in EO-2 turns no line red anywhere in the repository, and `L-10`'s drift is not an oversight anyone made — it is the expected condition of an unasserted copy. Counts are not safer for having a tool: the tool covers the sites it knows, and `dossier/00-INDEX.md` and `deploy/docker-compose.yml` each publish a suite count that the tool does not derive — they disagree with each other, and both disagree with the gate.

  *Checked by.* Nothing, in the direction that matters. `./tools/sync-counts.sh --check` reports drift in the counts it derives at the sites it knows, and this document is at none of those sites. The rule is kept by not writing the number, which is verifiable only by reading — deliberately, because the alternative is a copy that a passing gate makes look maintained.

**What this document does not cover.** Stated in the voice of ACP-SPEC-001 §4.2 and for its reason: an exclusion stated is one a reader can plan around, an exclusion implied is one they discover in production.

- **Substrate choice.** No database, queue, KMS product, container runtime, service mesh or cloud is named or required. §5 states properties a store must guarantee and cites the substrates ACP-SPEC-001 already names for the Consumption Ledger (CL-5); a store that provides the property is conformant however it is built, and a product name in a specification is a second definition of a requirement that the product may stop satisfying.
- **Orchestration and delivery.** Kubernetes manifests, Terraform, image build and deployment pipelines are out of scope. `deploy/` in the reference repository holds a Docker Compose demonstrator and nothing else, because the substrate is deliberately deferred. Where a check in this document asserts a property of that compose file, it is evidence about the demonstrator this repository publishes and no evidence at all about a production network; §9 records that bound where the assertion is defined.
- **Capacity planning.** Replica counts, instance sizes, queue depths and throughput targets are not specified. ACP-SPEC-001 states one requirement in this area — a shared ledger per tenant for multi-Executor deployments (CL-5) — and no count anywhere, including no replica floor for the ledger quorum that partition behaviour (CL-6) and check-then-mutate ordering (CL-7) presuppose. §8 declines to invent a backpressure policy for the same reason it declines to size one: the interaction it would rest on is recorded as unanalysed in ACP-SPEC-001 §15.
- **Availability.** No availability SLO is specified here, and none is specified in ACP-SPEC-001 §4.2 either. **But note**, in §4.2's own words, that DoS is not fully severable from safety: RES-2 discloses that every fail-closed control routes to ATTEST and that a flooded quorum converges to rubber-stamping (AT-7), silently converting floor-HIGH into effective-ALLOW. A deployment may hold itself to an availability target; presenting one as an ACP requirement misrepresents both documents, and reading the absence of an SLO as evidence that availability is safety-neutral is the inference §4.2 added its note to prevent.

This list is a scope statement and not a residual-risk list. Limits that bear on what a conforming deployment actually gets carry `DP-` ids in §10, so that `spec/vectors/OBLIGATIONS.md` can key to them: an unlabelled limit cannot be cited, and a limit nobody can cite is one nobody can be held to.

**Release integrity.** The rule in ACP-SPEC-001 §1 — every published revision immutable, any change to normative content incrementing the version, one version string mapping to exactly one artifact — governs this document and is adopted by reference rather than restated as a clause of its own, which is DP-3 applied to this paragraph. Two documents behind one version string is the collision that schema change control (SR-1) and bundle epochs (PB-5) prohibit in the system's own artifacts, and a deployment specification is no more exempt from that discipline than the specification it accompanies.

The key words **MUST**, **MUST NOT**, **REQUIRED**, **SHALL**, **SHALL NOT**, **SHOULD**, **SHOULD NOT**, **RECOMMENDED**, **MAY**, and **OPTIONAL** are to be interpreted as described in RFC 2119 and RFC 8174 when, and only when, they appear in all capitals. This paragraph is the one passage this document reproduces from ACP-SPEC-001 §1, and it is reproduced rather than cited because in both documents it is a citation of RFC 2119 rather than a requirement of ACP-SPEC-001 — a document that uses the keywords without adopting their definition has not defined its own terms. The exception is argued here rather than taken silently, which is the discipline DP-3 states.

## 2. Trust-Domain Topology (Normative)

A trust domain here is **a set of entry conditions**, not a region of a picture. The domain is defined by what **MUST NOT** cross into it and by what a component inside it is permitted to hold; the boxes and arrows a reader may have seen elsewhere are a rendering of that set and are not the set. This distinction is the reason this section exists rather than a diagram. The artifact this section replaces — `docs/private/acp-deployment-architecture.html` — drew seven domains, six with a dashed border and one solid, and its legend defined the dashed border as "trust boundary — no implicit trust across" while never saying what the solid one meant. A reader could not tell whether the difference was normative, and no command could tell them, because that file is gitignored: outside the ten signed roots, outside `MANIFEST.sha256`, outside `tools/sync-counts.sh`, and outside the clause-id uniqueness assertion in `tools/selftest.sh`. **A normative document outside the signed roots is not normative.** That is the defect this section corrects, and the corrections published below are the drift that accumulated while nothing could read it.

This section **adds** substrate-level obligations. It does not restate the isolation requirements that already exist. Tenant separation and the soft-boundary disclosure (**D-1**, §12), the model path's absence of route (**D-2**, §12), Bundle Repository isolation (**D-3**, §12), the isolation boundary itself (**§9.1.1 step 3**), transport (**§12.2**), and reconciliation placement (**§11.3**) are cited by reference throughout and are **not** paraphrased anywhere in this document. Restating them in different words would put two descriptions of one obligation into the corpus, which is the encoding-split defect that the audit chain correction (**AU-1**) and the bundle signature correction (**PB-8**) were each about — both of which survived a full release cycle because prose has no differential.

What this section adds is of one kind: **the deployment must be able to say where each component actually runs, under which credentials, and what it holds** — facts the specification requires to be true but never requires anyone to write down. An obligation nobody records is an obligation nobody can audit, and §10's single-component invariant analysis is only as good as a reader's ability to check that two of its rows are not the same host.

- **DP-5. The seven trust domains, and the deployment record that names their members.** A conformant deployment **MUST** assign every component it runs to exactly one of seven domains — **untrusted**, **control plane**, **offline authoring**, **approval**, **independent notification**, **external verification**, **effect** — and **MUST** publish a **deployment record** naming, for each domain, its member components, the host or hosts each runs on, the credential domain each authenticates under, and the network destinations reachable from it. A component assigned to no domain, or to two, **MUST** be treated as a topology defect and **MUST** be resolved before the deployment is described as conformant with this document.

  *The deployment record is not a control input, and this is the constraint that decides its shape.* The record is written by the deploying party and is read by **auditors, assessors and operators — and by nothing at runtime**. No component **MAY** weight any decision on it, and no verifier **MAY** read a domain assignment, a host name or a credential-domain name out of it in order to grade a Proposal, admit a signature or release an action. A deployment describing its own isolation to a verifier is a derived security value supplied by the party under verification, which is the class ACP-SPEC-001 has now hit five times (C2 → X1 → Y1 → Z3 → W1), each time inside machinery the previous fix introduced. The bundle manifest's `custody` object already occupies exactly this posture — required, recorded, classified **T**, and read by nothing — and the deployment record takes the same one deliberately. **If a future revision gives a runtime component a reason to read this record, that revision has introduced the sixth recurrence, in the machinery written to describe the fifth.**

  *Why seven and not a different number.* The seven are the domains the existing controls already presuppose: the untrusted domain because §5.1's Door B is inert rather than filtered; offline authoring because policy bundle signing (**PB-1**) requires an offline key; approval and independent notification because the notification path independence rule (**DR-2**) requires two of them and forbids a shared renderer; external verification because anchor verification (**AU-4**) and reconciliation (**§11.3**) are both normatively placed outside production; the effect domain because §5.1a forbids a third route; and the control plane because everything else is in it. The list is an enumeration of existing obligations, not a new taxonomy.

- **DP-6. Untrusted domain: no signing key, and the adapter's side of the line is stated.** No component in the untrusted domain **MAY** hold a private key used to sign a Proposal, a Decision Receipt, an Attestation Object, a bundle, an audit record or an anchor submission. Its routes are constrained by the model-path rule (**D-2**, §12), which this document does not restate. In addition, the deployment record **MUST** name every credential issued to a component in this domain and **MUST** state, for each, the domain it authenticates *to*.

  *The adapter placement the diagram never resolved.* §4.3 classifies the **Ingress Adapter (F-HIGH)** as "Trusted for shape, not for intent" and the **Ingress Adapter (F-LOW) / translator model** as "**Untrusted.** Always." A deployment **MUST** place the F-HIGH adapter in the **control plane** domain and the F-LOW adapter and every model-serving component in the **untrusted** domain, and **MUST** state which it runs. This matters because the fidelity class rule (**B-6**) requires the class to be stamped by the adapter and **MUST NOT** be settable by the client: a deployment that runs its stamping adapter inside a domain it has declared "assumed compromised" has an attacker-chosen fidelity class and no clause violated on paper. The replaced artifact placed "builds typed proposals" wholly inside the untrusted domain and never named an adapter at all, so the question could not be asked of it.

  *A transport client credential is not a signing key.* Components here **MAY** hold one, because transport (**§12.2**) requires mutual authentication on every inter-component link. See **DP-15**, which is where that distinction is made once for the whole document.

- **DP-7. Control plane: every inbound crossing is enumerated, and "one door" is false.** The deployment record **MUST** enumerate every point at which anything enters the control plane domain from outside it, and **MUST** attest that the enumeration is complete. The crossings this document is aware of are: (i) validated Proposals from ingress; (ii) signed bundle bytes arriving from offline authoring into the Bundle Repository; (iii) Attestation Objects and their signatures returning from the approval domain; (iv) acknowledgement and repudiation returning from the independent notification domain (**DR-4**, **DR-9**); and (v) the network time source, which **§12.5** makes a normative dependency by requiring NTS (RFC 8915) and capping Decisions at ATTEST without it. **An inbound crossing not in the deployment record is a topology defect, whether or not it appears in this list** — the completeness attestation is on the deployment, because this list is what one document's authors could enumerate and the next deployment will have a crossing they did not think of.

  *A published correction: "the only inbound door".* The replaced artifact labelled the API gateway "the only inbound door", and its own edges falsify the label: attestation objects enter the KMS and acknowledgement enters the Executor, both crossing the control-plane boundary from outside, and the time source crosses it without being drawn at all. The claim is true of *Proposals* and of nothing else. It is recorded here rather than fixed silently because the failure mode it illustrates is the one this clause is written against: a topology claim that is false about its own picture will be false about a deployment built from it, and nothing catches either.

- **DP-8. Offline authoring: state the mechanism, and do not claim more than the mechanism.** The deployment record **MUST** state the mechanism by which the offline signing key required by the bundle signing rule (**PB-1**) is held and the mechanism by which signed bundle bytes reach the Bundle Repository. A deployment **MUST NOT** represent the authoring host as air-gapped in any external claim unless it has implemented one — this mirrors tenant separation's soft-boundary sentence (**D-1**), which forbids representing container isolation as hardware isolation, for the identical reason. The word "air-gap" appears **zero** times in ACP-SPEC-001; **PB-1** requires an *offline key held by the security-policy role, distinct from all runtime keys*, which is a custody requirement and not a network-topology one. The replaced artifact printed "air-gapped · no network, ever", which is a stronger claim than any clause supports.

  *One-way distribution is a deployment mechanism, never the control.* Bundle read-only-ness to the runtime is guaranteed by cryptography under the bundle key custody rule (**PB-4**) — runtime components, including a fully compromised Policy Engine, hold no key that produces a valid bundle signature. A deployment **MAY** additionally enforce one-way transport; it **MUST NOT** describe that transport as the reason the bundle cannot be forged. The replaced artifact labelled this edge "one-way (diode)", a term that appears nowhere in the specification, and a reader who takes the network topology for the control will relax the cryptographic one when the topology is inconvenient.

  *Key custody mechanism is out of scope here.* Custody tiers are specified in **§4 (Key Custody)** of this document. This clause obliges the deployment to *state* the mechanism; §4 governs what the mechanism may be.

- **DP-9. Approval domain: attester keys never leave the attester's device, and the operator is not in it.** No component of the control plane **MAY** hold, escrow, proxy or recover an attester's private key, and the deployment record **MUST** state where each attester key is held. The operator **MUST NOT** be a member of the approval domain for any Proposal they originated, which is the attestation distinctness rule (**AT-2**) expressed as a topology obligation rather than a per-decision one: **AT-2** is checked at decision time against identities, and this clause is what makes that check auditable against infrastructure. A deployment in which one credential can both originate a Proposal and sign an Attestation Object for it satisfies **AT-2** on every individual decision and defeats it in aggregate.

  *What this does not do.* It does not address the presentation service, which is TCB per assumption **A-8** and is covered by **DP-13**, nor device-side re-rendering (**§12.6**), which is a SHOULD and remains one.

- **DP-10. Independent notification: distinctness is a deployment property, and it is not enough.** The notification service **MUST** run on infrastructure distinct from every component of the approval chain, under a distinct credential domain, and the deployment record **MUST** name both. The notification path independence rule (**DR-2**) already requires structural distinctness of the *rendering path* and states that a shared formatting library is a conformance failure even when it renders honestly; this clause adds that the distinctness **MUST** also hold at the substrate, because a shared host with a shared service account is a single compromise that reaches both renderers whatever their source trees look like.

  *This does not close notifier self-certification, and must not be read as doing so.* The notifier self-certification finding (**T-32**, in **ACP-CLASS-001**) is **OPEN**. Separate hosts and separate credential domains improve build-time and run-time provenance and change nothing about the classification: the Executor still reads `note.source_path`, `note.from_canonical` and `delivered` from the notifier, which is the party it is verifying, and those rows remain **T**. Closing **T-32** means the Executor checking two distinct signed service identities named in the signed bundle. **No amount of topology closes it**, and a deployment record that lists two hosts is not evidence that it has been closed.

- **DP-11. External verification: name the party, and prove it holds no production credential.** Anchor verification (**AU-4**) and reconciliation (**§11.3**) are both already placed outside the production trust domain by ACP-SPEC-001, and this document does not restate the requirement. What it adds is the record: the deployment record **MUST** name the party that operates anchor verification and the party that runs the reconciliation job, the infrastructure each runs on, and the credentials each holds — and **MUST** state that neither holds any credential valid in the production domain, including read credentials on the audit database, the Consumption Ledger or the Bundle Repository.

  *What breaks without it.* §11.3's rationale is exact: reconciliation inside production writes its findings to the chain it audits, by a party inside the domain under suspicion. A reconciliation job that runs outside production but authenticates *into* it with a production service account has satisfied the sentence and not the reason for it — its credential is exactly what a production compromise obtains. The replaced artifact placed nothing at all in this domain but an anchor service; the reconciliation job has no box in it, and eight normative checks (**§11.3** (a)–(h)) therefore had no home in the repository's only topology artifact.

- **DP-12. Effect domain: enumerate the targets, and do not credit them with verification they do not perform.** The deployment record **MUST** enumerate every external system the Executor can affect, the credential scope held for each, and the action classes mapped to it. No component other than the Executor **MAY** hold a credential to any enumerated effect system. This is the auditable form of the no-third-route rule (**§5.1a**): "any component capable of causing an external effect on the strength of anything other than a verified Decision Receipt (**B-4**) is a Door A bypass and a conformance failure" is a property of a *deployment's credential map*, and the credential map is the artifact in which a third route is visible.

  *A published correction: what B-4 binds.* The replaced artifact labelled the effect-domain boundary "no route in but a verified Decision Receipt (B-4)". **B-4** constrains the *Executor's inputs* — the Executor **MUST NOT** accept an instruction from any channel other than a verified Decision Receipt. It imposes nothing on the target systems, and no clause anywhere requires a laboratory system, an ERP or a partner API to verify a receipt. As drawn, a reader may believe the effect systems check something. They do not, and the guarantee is entirely upstream: it rests on the Executor being the only holder of the credentials, which is why this clause is written as a credential obligation rather than a network one.

- **DP-13. The three TCB components MUST be separately isolated and separately named.** The Attestation Presentation Service, the Consumption Ledger and the Bundle Repository are TCB (§4.3, and residual **RES-5**). This document does not restate why. It adds that they **MUST** be isolated **from each other** — distinct hosts and distinct credential domains — and that the deployment record **MUST** name all three as TCB, individually.

  *What breaks without it, and it is a defect in the analysis rather than in a control.* §10's invariant analysis is stated per **single** component compromise, and it concludes that compromise of the Attestation Presentation Service or of the Consumption Ledger defeats INV-1-HIGH while compromise of the Bundle Repository does not, *provided §9.1.1 step 3 isolation holds*. Co-locating any two of the three makes one compromise satisfy two rows at once, which converts the single-compromise analysis into a two-component one without changing a single sentence of it. §10's own closing paragraph already states that "two-component collusion exceeds the stated invariant". A shared host is collusion procured for free.

  *Why the naming half is separate from the isolation half.* The replaced artifact marked TCB on the Attestation Presentation Service alone and drew the Consumption Ledger and the Bundle Repository as ordinary cylinders, visually indistinguishable from the audit chain store, which is **not** TCB. Two of the three components that entered the TCB were therefore invisible as TCB in the only topology artifact the repository had, and **RES-5** names them precisely so the residual is auditable. An unnamed TCB component is the state **RES-5** exists to end: "they were load-bearing in v1.2.0 too, but unnamed."

- **DP-14. Bundle Repository: name the host and the credential domain, separately from the Policy Engine's.** The isolation requirement is **D-3** and **§9.1.1 step 3**, which states that "the isolation boundary **MUST** be stronger than filesystem permissions on a host shared with the Policy Engine — separate host, separate credential domain, or hardware-enforced". That text is cited, not restated. This clause adds the record: the deployment record **MUST** name the host on which the Bundle Repository runs, the credential domain under which it authenticates, and the corresponding two facts for the Policy Engine runtime, and **MUST** state which of the three permitted boundaries the deployment implements.

  *Why the record and not just the requirement.* **D-3** and **§9.1.1 step 3** are satisfiable or not as a matter of fact about a deployment, and there is no artifact in which that fact is written down, so the requirement is unfalsifiable in practice — an assessor can read the clause and cannot check it. §10's Bundle Repository row is explicitly conditional: "**No violation** *if §9.1.1 step 3 isolation holds*". A conditional invariant whose condition is unrecorded is an invariant nobody can evaluate. The replaced artifact drew the Bundle Repository and the Policy Engine inside one undivided control-plane rectangle with no boundary between them, which is the strongest available evidence that this fact goes unrecorded when nothing asks for it.

- **DP-15. Signing keys and transport credentials are inventoried separately.** The deployment record's key inventory **MUST** separate, per domain, (i) **application-layer signing keys** — receipt, attestation, bundle, audit-anchoring — from (ii) **transport client credentials** used to satisfy mutual authentication (**§12.2**) and from (iii) **target-system credentials** held by the Executor. A claim that a domain holds "one key" or "no key" **MUST** state which of the three categories it is about.

  *A correction worth recording, and it is falsified by its own sentence.* The replaced artifact's control-plane subtitle read: "isolated segment · mTLS on every link (12.2) · the only private key here is the KMS receipt key". Transport (**§12.2**) requires mTLS on every inter-component link, and mutual TLS means every service in that domain holds a client private key; tenant separation (**D-1**) independently requires dedicated per-tenant *executor credentials*. The second half of the sentence is contradicted by the first half of the same sentence, and by a clause the same sentence cites. The correct claim — and the one this document makes — is that **the receipt signing key is the only application-layer signing key in the control plane**, which is a real and load-bearing property: it is why a compromised Executor cannot mint a receipt, and it survives the correction intact. The reason the error is published rather than quietly repaired is that it is the shape a reviewer skims past, because both halves cite real clauses.

  *Interaction with the no-signing-key claim about the Executor.* The same artifact stated that the Executor holds "no signing key at all". Under this clause that reads: no *application-layer signing* key. The Executor holds transport credentials and target-system credentials by requirement, and stating it the other way makes a true and important custody property look like a false one on inspection.

- **DP-16. Component names are pinned to §4.3, and a second vocabulary is a defect.** Every component §4.3's trust-classification table names **MUST** be referred to by that name in the deployment record and in any deployment artifact: **Ingress Adapter**, **Input / Output Schema Validator**, **Policy Engine**, **Context Store**, **Attestation Presentation Service**, **Bundle Repository**, **Consumption Ledger**, **Executor**, **Audit subsystem**. Components §4.3 does not name **MUST** be named by the clause that introduces them — the **KMS** (§9.1.1), the notification service (**DR-2**), the anchor verifier (**AU-4**), and the reconciliation job (**§11.3**) — and the deployment record **MUST** give exactly one name to each.

  *Why a naming rule is normative.* The replaced artifact used "Policy service", "Executor service", "Audit service" and "Anchor service", which is a second vocabulary for a component set that already has one. Two names for one object is the encoding-split defect in prose form, and it compounds: the third document is written from the second, and by then the mapping back to §4.3 is a reader's inference rather than a fact. This is the identical failure the audit chain correction (**AU-1**) and the bundle signature correction (**PB-8**) each recorded in the normative source itself, one register down.

**What this topology does not show or require.** Absence is legible in a list and invisible in a diagram, which is most of the argument for replacing one with the other. This section does **not** state, and a deployment **MUST NOT** infer from it:

- **Any network mechanism.** Firewall rules, service meshes, egress proxies, data diodes and VPC layout are all deployment choices. The replaced artifact drew an egress proxy that it honestly labelled "deployment hardening — not specified" and then routed the only consequential flow through it, making an unspecified component load-bearing in the picture. This document names credentials and hosts, and leaves mechanisms to the deployment.
- **Any tenancy multiplicity.** Tenant separation (**D-1**) governs it and this section adds nothing. The domains above describe one tenant's topology; a multi-tenant deployment satisfies **D-1** or does not, and this section will not tell it which.
- **Any replica count, quorum size or failure domain.** No clause in ACP-SPEC-001 states one either — the ledger partition rules (**CL-6**, **CL-7**) presuppose a reachable majority without ever specifying a replica count. That gap is real and is not filled here.
- **Any behaviour of a component that is starting, restarting or degraded.** Cold start is §6 of this document; dependency loss is §7. A domain assignment says nothing about either.
- **The full component set.** §4.3 names an **Input / Output Schema Validator** that the replaced artifact drew nowhere, an **operator** who has no box in it, and a reconciliation job with no home; boundary rules **B-1** and **B-3** both depend on the first. They are named in **DP-16** and assigned in **DP-5**, and this section requires nothing further of them.
- **Any evidence that a real deployment is isolated.** This is the limit of the whole mechanism and it is stated rather than buried: every clause above is an obligation on a deployment that this repository cannot observe. The deployment record is the deployment's own account of itself, classified in **DP-5** as read by auditors and by nothing at runtime. It moves the trust from the message to the deployment process; it does not eliminate it, and no test in any repository could.

*Coverage, stated plainly.* **No command in this repository goes red today for a violation of any clause in this section.** Nothing reads `deploy/docker-compose.yml`, nothing parses a deployment record — none exists — and no gate can observe a host, a credential domain or a network route. §9 of this document records, per clause group, the executable-consumer status of the clauses in it; **nothing in this section claims one**, and any check that later covers the demonstrator's own compose topology is evidence about this repository's compose file and no evidence at all about a deployment. A section whose subject is that self-certification is the recurring defect is not entitled to self-certify its own coverage, so the number of clauses here with an executable consumer is stated as what it is: zero.

## 3. Deployment Profiles (Normative)

The word *profile* appears nowhere in ACP-SPEC-001, and neither does *custody*. This section is new normative text and says so rather than dressing itself as a restatement. What it is new *about* is narrow: a profile selects among obligations the specification already states, and fixes two values the specification already requires a deployment to choose — the suite floor (CR-4) and the arrangement under which the offline bundle key is held (PB-1). It invents no control, and it grants no relief from any requirement.

One constraint decides the whole mechanism, and it is stated before any profile is named, because a profile defined the obvious way is a security defect rather than a convenience: **the profile is established out-of-band at the verifier and is never claimed in the bundle or the message.**

- **DP-17. A deployment profile is a named set of obligations, and nothing else.** A profile **MUST** be defined as (i) a set of obligations drawn from ACP-SPEC-001 and from this document, and (ii) a custody floor, and a suite floor for each signed structure class the profile constrains, each named as a value. A signed structure class a profile does not constrain keeps the deployment's ordinary floor under CR-4; a profile is not required to name all four. A profile **MUST NOT** be defined as a level, a grade, a score, or any other quantity that admits comparison.

  *Rationale.* Everything in this section follows from the profile being a set. A profile defined as a quantity is a conformance level wearing a different word, which DP-23 forbids for reasons the specification has already paid for once, and it is a rankable object, which DP-20 forbids for reasons the specification has already paid for twice.

- **DP-18 (Normative). A deployment profile MUST be established out-of-band at the verifier.** A profile identifier **MUST NOT** appear in the Policy Bundle, in `manifest.json`, in a Decision Receipt, in an Attestation Object, or in any message on any inter-component link. A verifier **MUST NOT** read a profile identifier from any of those places if one is present. Presence is not an error to be repaired and not a value to be reconciled — it is ignored, and the verifier's own deployment-time configuration is the only source.

  *Rationale, and it is the reason this section exists.* A verifier must never accept a derived security value from the party it is verifying (TR-8, generalized to relations at TR-10, disclosed as RES-8/RES-9/RES-10). That class has recurred five times — C2 → X1 → Y1 → Z3 → W1 — each time inside machinery the previous fix introduced. A self-certified profile would be the sixth, and it would land inside the machinery introduced to *describe* the fifth: this document exists to write the deployment arrangement down, and the shortest way to write it down is to stamp its name on the artifact everyone already reads. The shortest way is the defect.

  It is also a worse instance of the class than the custody claim already disclosed beside it. `manifest.custody` is classified **T**, read by nothing, and names how one key is held. A profile names the whole arrangement in one token, so a signer able to write it moves the verifier's suite floor, its custody floor, its anchoring obligation and its notice obligations together, with one string.

  *What breaks without it.* A compromised or merely careless signer emits an artifact naming the least demanding profile; the verifier adopts that profile's suite floor; and the floor CR-4 places in the signed bundle *precisely so that a downgrade cannot be negotiated at runtime* has been negotiated at runtime. The check reports satisfaction. Nothing in the verification path is defective — the wrong question was asked, correctly.

  *Signing it does not fix it, and this is the tempting answer.* A profile carried inside the signed bundle is still a claim by the party under verification about how strictly it wishes to be judged, authenticated rather than corroborated. Signing a self-assessment does not make it an assessment by someone else. The same reasoning retires the variant in which the profile travels in a receipt: the KMS signs receipts, and §10's invariant analysis already assumes a compromised KMS.

- **DP-19. The profile has no parser.** An implementation's profile type **MUST NOT** provide a deserialiser, a wire decoder, or a constructor from any string received over any link; it **MUST** be constructible only from the verifier's local configuration. The Policy Bundle schemas **MUST NOT** declare a `profile` property, a `deployment_profile` property, or any equivalently-named field.

  *Rationale, and the asymmetry is the point.* Signature suites do parse — a suite is announced by the signer and then *checked* against a floor that lives in the signed bundle (CR-1, CR-4) — and announcing a suite therefore costs nothing, because the announcement is not believed. A profile is never announced at all, so a parser for it decodes an input no honest party sends. Its only reachable caller is an attacker. This copies the shape `acp-crypto`'s custody tier already has, where the absence of a wire decoder is documented as deliberate rather than left to look like an oversight, for the same reason.

  *What breaks without it.* Not the first release. A profile type that can be built from a string is inert while no call site does so, and becomes a live downgrade the first time someone adds a diagnostic that echoes the bundle's declared profile, or a migration that "prefers the bundle's value where present". The parser is the thing that makes that edit a one-liner, and DP-18 is one review away from being the only thing holding it.

  *Not checked today.* No implementation in this repository reads, refuses, or represents a profile, so nothing can go red. The cheapest check that would catch half of this clause is an assertion over the bundle schemas that no `profile`-shaped property exists; §9 records whether it ships and what it costs. Note the half it would not cover: it catches the field entering the wire format, not a verifier that learns the profile from somewhere else it should not.

- **DP-20. Profile satisfaction is CONTAINMENT, and there is no ordering over profiles.** A deployment satisfies a profile iff **every** obligation that profile names is discharged. There **MUST NOT** be a "higher profile" relation, a ranking function, a numeric level, or any comparison operator over profiles, and no clause, configuration or implementation may express one. A verifier configured for a profile checks that profile's obligations, and **MUST NOT** accept a deployment on the grounds that some other profile it satisfies is stronger. Where one profile's obligation set does happen to contain another's, that is a fact about two sets and **MUST NOT** be used as a rule.

  *Rationale, and it is the published CR-4 correction one register up.* The first cut of `Suite::satisfies_floor` mirrored the reference's rank table — `{ed25519: 0, slhdsa128s: 1, hybrid: 2}` — and asked whether the offered suite ranked at or above the floor. Suites are sets of primitives and those sets are incomparable: `hybrid-ed25519-mldsa65` is `{classical, ML-DSA}` and contains no SLH-DSA, yet it outranked `slhdsa128s`, so a deployment whose floor said *hash-based post-quantum, resting on no lattice assumption* was served a lattice signature and told its floor was met. That is not a stronger suite accepted; it is one hardness assumption substituted for another against an offline policy decision. Both implementations agreed on the table, and a passing test asserted it — the standing warning about differential evidence applies: agreement is evidence about consistency, never about correctness.

  A profile is a worse candidate for ranking than a suite was, not a better one. It bundles a suite floor, which is a set and is provably incomparable, with a custody floor, which is a chain and legitimately ranks (§4), with obligations that are neither. No proof exists that any two profiles are comparable, and the profiles below include a pair that demonstrably are not: DP-26's suite floor contains no classical primitive and DP-25's contains no SLH-DSA, so neither contains the other in either direction. Ranking them would re-commit CR-4 with a wider blast radius, because a profile decides more than one thing at a time.

  *Cost, stated plainly.* A deployment cannot advertise "at least profile X". It names the profile it was configured against, and a deployment discharging two profiles' obligations is configured for two. That is more verbose than a ladder, and it is the intended outcome — CR-4 records the same merit: containment forces a deployment that genuinely wants either of two arrangements to say so as two floors, rather than smuggle it through an ordering.

- **DP-21. An unconfigured profile is a refusal, never a default.** Where a verifier holds no profile configuration for the identity it is verifying, it **MUST** refuse. It **MUST NOT** select a default profile, fall back to the least demanding one, or infer a profile from anything it observes at runtime.

  *Rationale.* This is *unknown is never LOW* (P-4) at the profile boundary, and the custody boundary already enforces the identical rule: the verifier's trusted-key table answers `None` for a key it was never configured with, and `None` is a refusal rather than "unknown, assume something reasonable". Inference is the interesting failure, not the bare default. A verifier concluding "this deployment names no notice recipients, so it must be running the profile that does not require them" has let the deployment choose its own profile by omission — DP-18 defeated with no identifier ever transmitted, and no artifact to point at afterwards.

  *Not checked for profiles.* The analogous custody assertion exists and passes, and covers the key ladder rather than the profile above it. See DP-22 for exactly what it does cover, and §9 for the rest.

- **DP-22. A profile's custody floor is evaluated against the verifier's out-of-band record of the key, never against the key's own claim.** Each profile names a custody floor over the ladder defined in §4 (Key Custody). A verifier **MUST** answer *is this key held at or above the floor* from configuration recorded when it was deployed, keyed by the key's fingerprint taken over the complete suite, and **MUST** answer that a key it was never configured with satisfies no floor at all. Every custody floor in this section is written out as *custody tier* `Tn`, per §4, and never as a bare tier token.

  *Why the long form is mandatory rather than tidy.* Resource floors already bind `T0`–`T3` to sensitivity (RK-1), and every other clause in the specification means that ladder by "tier". The bundle schema that carries both says it directly: they share a scale, not a subject. A bare `T2` in a deployment document resolves to two different normative meanings, which is the `CL-7` defect — one identifier naming two rules — reappearing at the level of a token rather than a clause id. It resolves in the direction that relaxes a control about half the time, and no check in this repository can see it.

  *What is checked, and where — stated narrowly on purpose.* Three tests in `crates/acp-crypto/src/custody.rs` hold the mechanism this clause requires: one configures a verifier to believe a tier for a key whose holder knows a different one and asserts the verifier answers from its own configuration; one asserts an unconfigured key has no tier and meets no floor; one asserts a floor refuses a weaker tier and accepts a stronger one. Delete the out-of-band lookup and they go red. They run under `cargo test --workspace` from `tools/selftest.sh`, **not** from the per-commit gate, and that block is skipped with a notice when `cargo` is absent. Citing them as gate-enforced would overstate them, and they cover the key ladder only: no profile sits above them in any implementation here.

- **DP-23. A profile MUST NOT relax any MUST or MUST NOT of ACP-SPEC-001, and satisfying one is not a conformance claim.** *Door A Conformant* is defined at ACP-SPEC-001 §14 as an unconditional property over §§2–15. A profile may only **add** obligations to that baseline, or **fix** a value the specification requires a deployment to choose. A deployment claiming a profile **MUST** also state, separately, whether it is Door A Conformant; the two claims are independent and neither implies the other.

  *Rationale.* The move this forbids has a named precedent one door over: adding a content filter and relaxing a Door A control on the strength of it is an explicit conformance failure (§5.1a). A profile permitting a deployment to skip, say, multi-party anchoring (AU-3) is the same move with an administrative label instead of a technical one. It also makes the claim unfalsifiable in the way the duplicated `CL-7` was — two deployments would both say "conformant under our profile" while satisfying disjoint requirement sets, and both would be telling the truth.

  *Why this document is a separate document, and not §16.* §14's conformance range is `§§2–15` of ACP-SPEC-001. Obligations added as a new section inside that range would join the conformance surface automatically and silently, redefining what conformance means for every implementation already assessed — a substantive normative change smuggled in through a section number. Sitting outside the range makes extending it an explicit act, taken deliberately in the specification or not at all.

*Why these names, and not Essential / Regulated / Critical.* Those were the working names and they were dropped before drafting rather than kept with a warning attached. They read as an ordinal ladder — *essential* is the floor, *critical* is the top — and DP-20 spends its whole length saying there is no ladder. A clause forbidding the reading its own names invite is strictly weaker than not inviting it. Each name below states the one thing that distinguishes that profile, and the three are deliberately drawn from different axes — who verifies the audit chain, how the key is held, who fixes the mechanism — because there is no single axis. Two profiles sharing most of their obligations is expected and is not a relation between them (DP-20).

- **DP-24. Profile `single-domain`.** One organisation operates the control plane and also operates the anchor verifier. Its obligations, additional to the ACP-SPEC-001 baseline:

  - The bundle is signed with an offline key held by the security-policy role and distinct from all runtime keys, with author and reviewer identities distinct (PB-1, PB-2). Policy is read-only to the runtime **by cryptography** rather than by file permissions (PB-4); the authoring host's isolation is a separate obligation, stated in §2 of this document.
  - Custody floor: custody tier T1.
  - Bundle-signature suite floor: `hybrid-ed25519-mldsa65`, satisfied by containment (CR-4).
  - Tenant separation, the model-path route ban, and bundle-repository isolation as already required (D-1, D-2, D-3 with ACP-SPEC-001 §9.1.1 step 3).
  - External anchoring by one of the mechanisms multi-party anchoring (AU-3) permits, every anchor independently verifiable by any holder of the anchor public keys (AU-3a), verified on schedule by a process outside the production trust domain (AU-4).

  *A deviation from a SHOULD, recorded rather than passed over.* CR-6 recommends SLH-DSA for bundle signing and audit anchoring, and this profile names a hybrid lattice suite instead. The reason is operability, not disagreement: `slhdsa128s` is declared and fails closed in both implementations (DP-27), so a profile naming it as the floor for the common case would be a profile no deployment could run. DP-26 names it for the case where a mandate makes the assumption non-negotiable. A deployment able to operate SLH-DSA **SHOULD** raise this floor, which CR-7 permits at any epoch.

  *Its disclosed weakness, and it is why this is a profile rather than a shortfall.* Reconciliation must run in the anchor-verifier's trust domain and never the production domain (ACP-SPEC-001 §11.3), and a single-domain deployment satisfies that only in the weak sense of a separate credential domain under one operator. Under a whole-organisation compromise its findings are written by a party inside the domain under suspicion, which is the condition §11.3's sentence exists to forbid. A deployment configured for this profile **MUST** disclose that in its residual-risk statement, in the same way a deployment choosing `quorum_k` = 1 must disclose that it has collapsed INV-1-HIGH to single compromise (PB-6) rather than discover it later.

- **DP-25. Profile `separated-verification`.** Anchor verification is operated by a party that does not operate the control plane. Its obligations, additional to the ACP-SPEC-001 baseline:

  - Everything DP-24 names, except its custody floor, which this profile replaces, and its residual disclosure, which the next obligation discharges.
  - The anchor verifier and the §11.3 reconciliation job are operated by a party that does not operate the control plane, holding its own copies of the anchor public keys so that every anchor is independently verifiable by that party (AU-3a, AU-4).
  - Custody floor: custody tier T2 — **declarable and not operable here; see DP-27.**
  - Bundle-signature suite floor: `hybrid-ed25519-mldsa65`.

  *What it buys, and what it does not.* Anchor verification outside the production trust domain is the mechanism by which several disclosed residuals are said to be *detected* rather than prevented, and floor-HIGH anchoring before release exists so that the detection cannot be erased first (AU-7). Separating the verifier makes that detection survive a compromise of the operator; it converts nothing from detected into prevented, and this profile makes no such claim.

  *Satisfying this profile discharges every DP-24 obligation, and that is still not an ordering.* The custody floor discharges because custody tiers are a chain (§4); the residual disclosure discharges because the condition it discloses has been removed rather than waived. Stated precisely because this is exactly the case where a reader reaches for an ordering — and it remains no licence to accept a `separated-verification` deployment where `single-domain` was configured, or the reverse (DP-20).

- **DP-26. Profile `mandated-custody`.** An external mandate fixes the key-holding mechanism and the cryptographic assumption, rather than leaving either to the operator. Its obligations, additional to the ACP-SPEC-001 baseline:

  - Everything DP-24 names, except its custody floor and its bundle-signature suite floor, both of which this profile replaces.
  - Custody floor: custody tier T3 — **declarable and not operable here; see DP-27.**
  - Bundle-signature suite floor: `slhdsa128s` — a hash-based post-quantum signature resting on no lattice assumption, which is the arrangement CR-6 recommends for bundle signing and audit anchoring. **Declarable and not operable here; see DP-27.**
  - Retention per the mandate wherever it exceeds the specification's own floor, which AU-5 already provides for.

  *This profile is incomparable with `separated-verification`, and that is the demonstration DP-20 rests on.* Under containment, `slhdsa128s` is `{SLH-DSA}` and `hybrid-ed25519-mldsa65` is `{classical, ML-DSA}`. Neither contains the other, so `mandated-custody` does not satisfy `separated-verification`'s suite floor and `separated-verification` does not satisfy `mandated-custody`'s. A ranking function would have to place one of them above the other and would be wrong in one direction whichever it chose — which is what the retired rank table did to `slhdsa128s`, in this same pair, with these same two suites. The incomparability is not a hypothetical constructed to justify the rule; it is the defect the rule was written from.

  *What this profile does not include, said because the custody tier invites the opposite reading.* It does not require separated verification. A mandate that fixes hardware custody does not thereby supply an independent auditor, and custody tier T3 is not shorthand for *everything the other profiles have, plus an HSM*. A deployment needing both is configured for two profiles.

- **DP-27 (Normative Disclosure). Two of the three profiles above are DECLARABLE AND NOT OPERABLE in any build in this repository, and a deployment MUST NOT claim a profile it cannot operate.** Specifically:

  - Custody tier T2 and custody tier T3 are declared and not implemented. The `kms` and `hsm` Cargo features are empty; enabling one adds no backend, and the signer constructor refuses both tiers unconditionally even in a build with the feature on, because an in-memory key is not a KMS and accepting it there would put a T3 label on process memory. `OfflineSigner` is the only `Signer` implementation in the workspace. There is no `KmsSigner` and no `HsmSigner`.
  - Custody tier T1 signs for production and its key is wiped after one signature, which is what *air-gapped host, key zeroized after use* means when written as code. It is therefore an offline bundle-signing arrangement and is not a substitute for an online receipt-signing key at any tier.
  - The `slhdsa128s` suite parses and fails closed. Its primitive is named `pq-slh` and is deliberately not aliased to the ML-DSA primitive, so a bundle naming that suite is refused as unsupported rather than verified against a lattice key.
  - Consequently `separated-verification` and `mandated-custody` are names for arrangements this repository can describe and cannot produce. `single-domain` is the only profile whose custody floor and suite floor are both operable here.

  *Why this sits in the section that defines the profiles rather than in an annex.* A profile table carrying an HSM row and no such sentence describes a capability that does not exist, and the reader most likely to act on it is the one choosing a profile. Declaring a tier is not implementing it; the code states the same rule in the same words, and states it because a silent downgrade — a deployment believing its key is in an HSM while it sits in process memory — is the failure worth arranging the types to prevent.

  *What is checked.* Three Rust tests hold this disclosure true: one asserting custody tiers T2 and T3 are unavailable in a default build and are never downgraded, one asserting `slhdsa128s` parses while its primitive reports itself unimplemented, and one asserting the SLH-DSA primitive is not equal to the ML-DSA primitive. Any of the three becoming silently operable turns them red. They carry the caveat recorded at DP-22: `cargo test --workspace` from `tools/selftest.sh`, not the per-commit gate, and skipped when `cargo` is absent.

  *What is not checked, and cannot be.* Nothing asserts that a deployment claiming a profile can operate it, because no implementation here has a profile to claim. That is a per-deployment obligation. It is also the limit of the whole mechanism: DP-18 and DP-19 make a profile impossible to self-certify, and nothing anywhere establishes that a given operator configured its verifier with the right expectations. The design moves trust from the bundle to the deployment process. It does not eliminate it, and no test in any repository could.

*Status of this section's clauses.* Most of the clauses above have no executable consumer of any kind today, because no profile exists in any language in this repository — DP-22 and DP-27 are the exceptions, and both are exceptions only in part. No count is given here on purpose: this document publishes no number that nothing re-derives, and the number of checked clauses is exactly the kind that rots quietly the moment one is added. §9 (Executable Consumers and Conformance Status) records which, per clause, and what each missing check would have to kill. Do not read the tests cited under DP-22 and DP-27 as coverage of the mechanism this section specifies. They cover the custody ladder and the suite primitives that the profiles are assembled from, and the assembly is the part that is unchecked.

## 4. Key Custody (Normative)

The word "custody" appears zero times in ACP-SPEC-001. The ladder this section makes normative — four tiers naming *how a signing key is held* — exists today in exactly two places, neither of them normative: `crates/acp-crypto/src/custody.rs`, which implements it, and `spec/schemas/bundle/manifest.schema.json`, which records a bundle's *claim* about it and classifies that claim **T**. In ACP-SPEC-001, offline bundle signing (PB-1) is the only key-custody **MUST** and it names no tier; floor change control (RK-5a) is a **SHOULD** that names a mechanism — an HSM with M-of-N authorization — without defining a ladder or requiring one. So this section is **new normative text, not a restatement**, and says so here rather than letting its citations imply a requirement ACP-SPEC-001 does not contain. It does not alter what ACP-SPEC-001 §14 defines as Door A Conformant; §1 of this document fixes that relationship, and restating it here would be a second definition of one rule.

- **DP-28. Every tier reference MUST name its ladder.** In this document, and in any artifact that references custody tiers, a tier token **MUST** be written as `custody tier T2` or `resource floor T2` — a plural qualifier over a range (`custody tiers T0 through T3`) is equally compliant. A bare `T2` **MUST NOT** appear anywhere both ladders are in scope.

  *Rationale, and the ambiguity runs in the dangerous direction.* Resource floors (ACP-SPEC-001 RK-1) already bind these four tokens to *sensitivity* — resource floor T0 public/sandbox through resource floor T3 privileged — and every other clause in that document that says "tier" means that ladder. A reader meeting a bare token therefore resolves it to the floor, because the floor is the only ladder ACP-SPEC-001 has. `manifest.schema.json` states the collision plainly — the two "share a scale, not a subject" — and draws the custody value from `floors.schema.json` so one edit cannot leave two spellings disagreeing. That fixes the *encoding* and leaves the *reading* ambiguous, which is the half that relaxes controls: "signed at T3" read as a floor is a remark about a privileged resource and passes review; read as custody it is a claim about an HSM. A deployment can then discharge a custody obligation with a floor value and never notice. This is the duplicated-clause-id defect (ACP-SPEC-001 CL-8's renumbering) one register up — there, one id named two normative rules and a conformance claim was unfalsifiable because an implementation could satisfy either and cite it honestly.

  *Scope, stated rather than assumed.* The rule does not reach back into ACP-SPEC-001, whose bare tokens are unambiguous precisely because it has one ladder. Retro-legislating them would be a document-wide edit with no defect behind it, and a second manifest invalidation for a cosmetic gain.

  *Nothing checks this today.* No command in this repository greps for an unqualified tier token. The check that would catch a violation is a `tools/selftest.sh` assertion that every `T[0-3]` occurrence in this document is qualified by `custody tiers?` or `resource floors?` in the same noun phrase. It is **not shipped**, and it has a trap worth recording before anyone writes it: the assertion has to exempt tokens that are *mentioned* rather than used, because this clause quotes a bare token twice on purpose and would fail its own check. An exemption list is exactly where such a check goes quietly vacuous, which is a reason to write it carefully rather than a reason not to write it. Until it exists, DP-28 is a writing rule enforced by reading, and this section obeying it is evidence about this section and about nothing else.

- **DP-29. Custody strength MUST come from the verifier's own out-of-band configuration, keyed by key fingerprint.** A verifier **MUST** hold a mapping from signing-key fingerprint to custody tier, established when it was deployed, and **MUST** answer every custody question from that mapping alone. A key the verifier was never configured with **MUST** have no tier — not a default, not an inferred one — and **MUST NOT** satisfy any custody floor.

  *Rationale (RES-8).* A custody tier cannot be self-certified. "This was signed at custody tier T3" is a security-determining value read from the party being verified, which is the class that has recurred five times (C2 → X1 → Y1 → Z3 → W1), each time inside machinery the previous fix introduced — and a document whose subject is deployment posture is where the sixth would naturally live. The mapping is keyed by **fingerprint and not by name** because a name is what an attacker controls in the message, and the fingerprint covers both public halves: covering only the classical half would let two identities differing solely in their post-quantum key collide, which is pairwise-distinct attester keys (ACP-SPEC-001 PB-7) defeated at the point identities are named. An unconfigured key answering "no tier" rather than "unknown, assume something reasonable" is the deny default (ACP-SPEC-001 P-4) at the custody boundary — unknown is never the permissive answer.

  *Implementation requirement.* A conformant custody type has **no wire parser**. Signature suites are announced by the signer and checked against a signed floor; a tier is never announced at all, so a `from_wire` or a `Deserialize` on the tier type is not a convenience but the mechanism by which DP-30 is later violated by someone who does not know they are doing it.

  *What checks it, and where it does not run.* `TrustedKeys` in `crates/acp-crypto/src/custody.rs`, with two tests that go red if the out-of-band lookup is removed: `the_verifier_does_not_learn_the_tier_from_the_signer` configures a verifier to believe custody tier T3 for a key whose holder knows is custody tier T1 and asserts both answers, and `an_unconfigured_key_has_no_tier_and_meets_no_floor` asserts the refusal. Both run under `cargo test --workspace`, which `tools/selftest.sh` invokes and **skips entirely, with a yellow notice, when cargo is absent**. Neither runs in the per-commit gate `./tools/verify.sh --suites`. Citing them as gate-enforced would overstate them. The no-parser property in the paragraph above is enforced by **absence** and by nothing else: adding a deserialiser to the tier type fails no test in this repository, so that part of DP-29 is held by review, not by a command.

- **DP-30. A custody claim carried in a bundle is documentation. A verifier MUST NOT weight any decision on it — and MUST NOT refuse on it either.** Both halves are normative. The claim **MUST** be classified **T** in the field-and-relation table (ACP-SPEC-001 §14 suite 12) and enumerated against a disclosed residual; an unlisted **T** is a conformance failure there. The residual is that an auditor reading the object is reading the signer's claim about itself, and it is this document's obligation to carry that residual in §10 rather than leave it implied here.

  *Rationale, first half.* This gives `manifest.schema.json`'s existing rule the normative citation it currently lacks: the schema already says a verifier **MUST NOT** weight any decision on the object, because a compromised signer writes it freely, and nothing but prose in a JSON file was carrying that. Normative text with no normative home is the mirror of this repository's recurring defect, and the schema comment has been the only statement of the rule since it was written.

  *Rationale, second half, which was reached by getting it wrong.* A verifier that refuses a bundle whose custody object is malformed or absent has let that field decide a verdict. It is then a refusal switch over a field nobody reads, operable by the compromised signer, requiring no defect anywhere else in the verification path — a denial of service delivered by the one object the design deliberately ignores. Tolerating garbage here is not laxity; reading it is the vulnerability.

  *What checks it.* Two pinned differential cases — `custody-absent` and `custody-malformed` in `tools/check-bundle-differential.py` — assert that both implementations still activate the bundle, and `a_field_no_verifier_reads_cannot_cause_a_refusal` in `crates/acp-bundle/src/verify.rs` asserts the same in Rust alone. Add a read that refuses, and they go red naming the field. Two limits, stated because the check is narrower than the clause: they run from `tools/selftest.sh` with a Rust toolchain, not from the gate; and they cover **bundle activation only**. No check anywhere asserts that an Executor, a KMS or a Policy Engine ignores the object, because none of those reads a bundle manifest in this repository yet.

  *A forward constraint on schema validation, stated now because the collision is already latent.* `manifest.schema.json` lists `custody` in its `required` set, and nothing validates a bundle against the schemas today — a limitation this repository discloses rather than hides. The moment schema validation ships, a bundle whose custody object is absent or wrongly typed is refused **by the validator**, which is the refusal switch this clause forbids, arriving through the well-formedness gate instead of through the verifier. Two normative requirements that cannot both hold is the DR-6 defect class, so the resolution is stated here rather than left to whoever wires the validator: when bundle-schema validation ships, the custody object **MUST** be exempt from refusal on invalidity, or its `required` and shape constraints relaxed to make it so. A field a verifier must not weight is a field whose malformation must not decide a verdict. The `custody-malformed` differential case is the check that goes red if a future validator forgets this, and it is worth noting that it only goes red because it was pinned in advance.

- **DP-31. The custody ladder.** A deployment **MUST** record, in its verifier configuration, one of the following tiers for each signing identity, and the tier recorded **MUST** name the mechanism actually holding the key.

  - **custody tier T0** — a passphrase-encrypted key file. Development only.
  - **custody tier T1** — an age- or GPG-encrypted key on an air-gapped host, the loaded plaintext wiped after use.
  - **custody tier T2** — a non-exportable cloud KMS key. The key never leaves, and it is online.
  - **custody tier T3** — a PKCS#11 HSM.

  *Why the cheapest tier exists at all.* A design that only works with an HSM is a design most deployments quietly bypass, and a bypassed control is worse than an absent one because it is still written down. The ladder is ordered by what each tier costs to operate, and every rung is a position someone actually occupies. What makes the table a control rather than a description is DP-33's refusal, not the table.

  *Encryption at rest is out of scope here, deliberately.* The tiers name mechanisms; they do not define a key-file format. `age`, `gpg` or a passphrase tool decrypts the file and the plaintext is handed to the signer. A bespoke container defined here would be a second definition of a solved problem, in the one place where getting it wrong is unrecoverable.

  *Nothing checks the honesty of the label, and this is assumption A-7's shape.* No check in this repository — and none is possible from inside it — compares a configured custody tier against the mechanism that actually holds the key. A deployment keeping a passphrase file and configuring custody tier T3 receives every answer a real HSM would receive. This is floor honesty (ACP-SPEC-001 A-7) transposed onto keys: the architecture can guarantee that nothing evaluates below a configured value and cannot know whether the value was set truthfully. A-7 is conceded unprovable and so is this. Two consequences follow and both are limits: DP-31 is an obligation on the deployment *process*, checked by that process or by nobody; and the tier list above is prose here and code in `custody.rs`, with nothing reconciling the two, so a divergence between them would survive every command this repository runs.

- **DP-32. A custody floor is compared by rank, and an unconfigured key clears no floor.** Where a deployment imposes a custody floor on a signing identity, the floor **MUST** be evaluated as a rank comparison over the DP-31 ladder: custody tier T3 satisfies a floor of custody tier T2, custody tier T1 does not, and a key with no configured tier (DP-29) satisfies no floor including the lowest.

  *Why ranking is legitimate here, when ranking suites was a published defect.* The signature-suite floor is **containment, not rank** (ACP-SPEC-001 CR-4), and the first Rust cut of it copied the reference's numeric suite ranking and thereby accepted a lattice-based signature against a floor demanding a hash-based one — a total order imposed on sets that are not comparable. The custody ladder is a single chain with **no incomparable pair**: each tier holds one key under one mechanism, and custody tier T3 does everything custody tier T2 does. That argument, not the shape of an enumeration, is what licenses `>=` here, and it does not transfer. A named deployment profile bundling several dimensions — custody, suite floor, quorum, notice targets — has not made the argument and **MUST NOT** inherit it. Note also the lesson recorded beside that correction: the wrong ranks were byte-for-byte agreed by both implementations and asserted by a passing test. Agreement is evidence about consistency, never about correctness.

  *What checks it.* `a_floor_refuses_a_weaker_tier_and_accepts_a_stronger_one` in `custody.rs`, whose failing assertion is spelled "a KMS key satisfied an HSM floor". Same cargo caveat as DP-29: it runs from `tools/selftest.sh`, not from the gate, and is skipped without a Rust toolchain.

- **DP-33. Tier policy: a development key MUST NOT sign for production, an air-gapped key MUST NOT sign twice from one load, and a tier the build cannot operate MUST refuse rather than downgrade.** Three obligations, each on the signing host:

  1. A signer at custody tier T0 **MUST** refuse to produce a signature designated for production.
  2. A key loaded at custody tier T1 **MUST** be wiped at the end of its first signature. A second signature from the same load **MUST** be an explicit refusal, never a silent re-use. The obligation is per *load* — the encrypted file persists; the decrypted key does not.
  3. A build asked for a tier it cannot operate **MUST** refuse, naming unavailability, and **MUST NOT** substitute a tier it can. Declaring a tier is not implementing it.

  *Rationale.* Custody tier T0 exists so the tooling is usable without a KMS, and the moment it can sign for production the other three tiers are decorative — an attacker picks the cheapest key that produces a signature anyone honours, and so does a hurried engineer. Obligation 2 is what "air-gapped host, key zeroized after use" means once it is written as code rather than as an intention. Obligation 3 targets the one failure worth arranging the design around: a deployment believing its key is in an HSM while it sits in process memory. It mirrors how a declared-but-unimplemented signature primitive fails closed (`pq-slh`, which parses because a deployment may name it and refuses because naming is not implementing).

  *The gap that decides what a deployment profile can promise.* **No tier in this ladder can be operated as an online production signer in this build.** Custody tier T0 is refused for production by obligation 1. Custody tier T1 may sign for production but costs a load ceremony per signature, which is not a hot path. Custody tiers T2 and T3 are **declared and not implemented**: their Cargo features are empty, so enabling one adds no backend, and the signer constructor refuses those tiers a second time unconditionally even in a build with the feature on — an in-memory key is not a KMS, and accepting it there would let an HSM label sit on process memory. Meanwhile the online production signer the architecture actually requires is the receipt signing key under KMS independence (ACP-SPEC-001 §9.1.1 and assumption A-6), whose mechanism — non-exportable, online — *is* custody tier T2, the tier that is declared and not implemented. So this ladder today governs the offline bundle-signing key (ACP-SPEC-001 PB-1) and nothing else. The receipt key's custody is specified by ACP-SPEC-001 §9.1.1 and by no tier in this section, and any statement that a deployment "runs at custody tier T2 or above" is a statement about bundle signing until that changes.

  *What checks it.* Three tests in `custody.rs`, each shipped with a deliberate counterpart so it cannot pass for the wrong reason: `t0_refuses_to_sign_for_production` beside `t0_still_signs_for_development`; `a_t1_key_does_not_survive_its_signature` beside `a_t0_key_survives_because_t0_is_a_development_tier`; and `t2_and_t3_are_unavailable_in_a_default_build_and_are_never_downgraded`. The cargo caveat from DP-29 applies to all three. Nothing separately checks the gap paragraph, because it is a statement about what the build cannot do; the three refusals are what constitute it.

- **DP-34. Split custody is a first-class case, and a split claim MUST report the weaker leg.** Where the classical and post-quantum halves of one signing identity are held under different mechanisms, the deployment **MUST** record the **weaker** of the two, both in its own configuration and in any claim it publishes.

  *Rationale.* Split custody is better than uniform custody, not a degraded fallback. Two-person authoring (ACP-SPEC-001 PB-2) requires author and reviewer to differ, and two identities holding different keys at possibly different tiers is the shape that requirement is asking for. Within one identity, hybrid composition is conjunctive (ACP-SPEC-001 CR-3): forging requires **every** primitive and therefore both keys, so an attacker must defeat both mechanisms and differing legs are not a weakness. The weaker-leg rule exists because a claim must never round in the flattering direction — reporting the stronger leg describes a key the attacker does not need to touch.

  *This clause cannot have a verifier-side check, and the reason is DP-30.* A verifier that read the custody claim in order to validate the weaker-leg rule would be weighting a value supplied by the party it is verifying, which DP-30 forbids. The rule is therefore an **authoring-time obligation only**, enforceable where the claim is written and by nobody afterwards. That is genuinely weaker than it reads, and saying so is preferable to shipping a check that would itself be the defect. The place it belongs is the signing tool, on the same argument the bundle CLI already makes for two-person authoring — it refuses at signing time because the verifier's refusal arrives later, on an air-gapped host, where nobody can see why, whereas the author is standing right there. No such assertion exists today.

*Coverage limit for the whole section, stated once.* Every check named above is Rust. The Python reference models no custody at all — no tier appears anywhere in `reference/src` — so the two-implementation bundle differential, which is what makes a divergence between readings visible elsewhere in this repository, covers custody only in the sense that neither side reads the claim. Custody here is **single-implementation**, it is exercised only under `tools/selftest.sh` with a Rust toolchain present, and a misreading of DP-29 through DP-33 by a second implementer is not something any current command would find.

## 5. Datastore Requirements (Normative)

This section states what each store must guarantee and — the part that decides deployments — what those guarantees constrain the substrate to be. It begins with what it does **not** do, because most of it is unenforceable from this repository.

It adds nothing to **retention**. Retention is already specified: CL-4 for receipt nonces, attestation ids and epoch high-water marks, CL-3 and L-27 for the DS-6f origin binding, L-17 for nonce size and ledger retention, AU-5 for Decisions, receipts, attestations and anchors. Those clauses are cited here and never restated, per the copied-limit rule (DP-4). A second statement of one retention period is a second definition of one value, and this specification has already published two corrections about exactly that shape — the AU-1 chain formula and the PB-8 signature schema — plus one it has not yet corrected: the end-to-end latency bound is stated three times in ACP-SPEC-001, and two of the three, the §13 limits row L-10 and the §9.7 performance note, were left behind by the v1.3.10 revision that split EO-2 by risk class.

What it adds is **durability**, which is specified nowhere. `fsync`, `backup`, `RPO`, `RTO`, `disaster` and `durabilit*` return no normative hit in ACP-SPEC-001 apart from AU-3's aside that WORM storage MAY be a durability *layer*. Every normative occurrence of the word `durable` is a requirement that some state **be** durable — RAD-3's high-water mark, §9.1.1 step 5's stored mark, DR-13's notice and its durable local commit — and none of them is a definition of what durable means, of who provides it, or of what a deployment must do when the state is lost. That gap is this section's subject, and one hole inside it (DP-40) is a live defect in ACP-SPEC-001 rather than a deployment question.

Nothing in this document boots. No test in this repository observes a storage engine, a replication factor, a backup or a restore. §9 records the coverage status of each clause group below, and where a clause has no consumer at all it says so in the clause rather than in a table someone might not read.

- **DP-35. Scope, and the criterion that decides it.** This section binds four stores: the **Consumption Ledger** (§9.3.1), the **audit chain store** (§11.2), the **Bundle Repository** (§9.1.1 step 3, D-3) and the **Context Store** (§8.7). Durability clauses — DP-38, DP-39, DP-42 — are stated for the first two only. The criterion is **re-derivability**: a Bundle Repository can be repopulated from the offline signing ceremony that populated it, and a Context Store's contents are re-sourced from the authoritative IdP/IGA under §8.7's authenticated sync, so losing either costs availability and fails closed while it is lost (§8.7 for Context, §7 of this document for the rest). The Consumption Ledger and the audit chain store are re-derivable from nothing. What has been consumed and what has happened exist only where they were written.

  *Why the criterion is stated rather than the conclusion.* A reader given a list of two stores extends it wrongly at the first new store; a reader given the test applies it. The test is also the thing that goes wrong first: a deployment that puts a re-derivable cache in front of a non-re-derivable store has moved that store into the first category in its own mind and not in fact.

- **DP-36. Ledger reads and claims MUST be served by a linearizable substrate, and the exclusion is the operative half.** Every read on which a claim decision depends **MUST** be served with linearizability per tenant (CL-1) and claimed with compare-and-swap or an equivalent atomic primitive (CL-2), on one of the substrates CL-5 admits. **Eventually-consistent stores, asynchronous read replicas, follower or stale reads, and any cache in front of the ledger — including one internal to a client library — MUST NOT serve a ledger read or a claim.** DP-40's refuse-only epoch cache is the single exception, and it is safe for the reason stated there: a stale value in it can only cause a refusal.

  *Why the exclusion needs saying when CL-5 already names what is acceptable.* An allowlist tells an engineer what to reach for; it does not tell them what to stop doing to the thing they already have. Putting a read replica in front of a hot table is the ordinary, competent response to load, and §8.7.1 explicitly **recommends** a lagging read-only replica for the Context Store. The two stores sit in the same diagram and take the opposite treatment.

  *Why they take the opposite treatment, which is the sentence to carry away.* A stale Context Store fails **closed**: a withheld capability produces DENY, and a stale tier raise produces more attestation — which is §8.7's stated reason Context compromise can no longer suppress escalation. A stale ledger fails **open**: a follower behind the primary reports a claimed nonce as absent, and §10's own row says what follows — "a ledger that falsely reports 'absent' reopens T-09 and T-14". The receipt executes twice, or the attestation is reused, with no attacker and no protocol defect. Copying the Context Store's replica guidance onto the ledger inverts the control while looking like consistency.

  *Not checked.* `reference/suites/partition_suite.py` and `reference/suites/partition_integration.py` exercise CL-1/CL-2/CL-6 semantics against the reference's in-memory quorum model, and both are in the per-commit gate. No command in this repository can see which substrate a deployment actually used, and no conformance vector can express it: a substrate choice is not an input-to-verdict relation.

- **DP-37. The substrate MUST distinguish "absent" from "cannot confirm absent".** A ledger client **MUST NOT** map a timeout, a quorum failure, a connection reset or a partial response onto the same return value it uses for a genuine miss. A substrate whose client cannot make that distinction at the call site is an **unsatisfiable configuration** and **MUST** be refused at deployment, in the DR-6 sense: rejected, not silently tolerated.

  *What breaks without it, and note the shape.* CL-6 requires the Executor to fail closed when the ledger cannot confirm absence, and CL-7 forbids resolving a security value by majority vote across disagreeing replicas; DP-37 is the substrate precondition both assume. That obligation is empty unless something can tell the Executor which of the two conditions it is looking at. A client library returning a cache-miss sentinel on timeout satisfies CL-6's text exactly and inverts it: under partition the Executor is told "absent", claims, and executes — the T-09 replay CL-6 exists to prevent, arrived at through a client library rather than through a missing check. This is a control defeated below the layer the control is written at, which is why it belongs in a deployment document and not in §9.3.1.

  *Why refusal at deployment rather than fail-closed at runtime.* The tempting fallback — treat every miss as unconfirmed and fail closed — is unsatisfiable, because a miss is the **normal** case for a fresh nonce. It would produce a permanent, total, silent outage on the honest path, which is the DR-6 defect class exactly: a configuration in which no legal request can ever succeed must be rejected rather than never released. Naming the refusal names what it prevents.

  *Not checked, and not checkable from here.* The reference raises a fail-closed error on a partition, so the partition suites' assertions hold against it. The distinction DP-37 requires exists only at the substrate boundary, and nothing in this repository crosses that boundary.

- **DP-38. A claim MUST be durable before it is reported as claimed.** The CL-2 compare-and-swap **MUST NOT** be acknowledged from volatile state. Acknowledgement **MUST** follow a write that survives loss of the acknowledging process and loss of any single failure domain in the ledger's replica set.

  *What breaks without it.* CL-4 sets a retention floor for nonces and attestation ids and makes epoch marks and origin bindings indefinite. Losing acknowledged-but-unwritten claims does not lose one identifier; it resets every identifier in the whole CL-4 retention window to unclaimed at once. That is T-09 receipt replay and T-14 attestation reuse at scale, produced by a power cut. It also silently converts DS-2's at-most-once into at-least-once against non-idempotent targets, which DS-4 forbids for floor-HIGH: DS-2's entire mechanism is claiming the identifier **before** the target call so that "a crash between claim and completion yields no execution, never a duplicate", and a claim that does not survive the crash it was written for is not a claim.

  *This constrains durability topology, not availability sizing.* DP-38 says a claim must outlive one failure domain; it does not say how many domains there are or where they sit, and DP-45 declines to say so deliberately. The two are consistent: surviving a failure is a property of the write, tolerating one is a property of the fleet.

  *Not checked, and the reference does not satisfy it.* `reference/src/acp_executor.py`'s `Ledger` holds nonces, attestation ids and origin bindings in Python sets and dicts. That is correct for what the reference is — it models linearizability and single-use, not storage — but it means no suite in this repository has ever executed a durable ledger. DP-38 ships with no consumer, and saying so is the alternative to implying one.

- **DP-39. Restoring a ledger from backup is a rollback and MUST be handled as one.** A deployment **MUST** (i) hold backups sufficient to recover the classes CL-3 and CL-4 retain **indefinitely** — epoch high-water marks and DS-6f origin bindings — because neither is recoverable from any other artifact, and (ii) after any restore, fail closed for the affected tenant until §11.3(a) and §11.3(c) reconciliation has run and named what was consumed between the restore point and the loss.

  *Rationale.* A restore to any point earlier than the most recent durable claim re-opens every identifier consumed since, and the restored store cannot tell you which those are — it is the store that lost them. The audit chain is the only record that survives the restored ledger and can enumerate them, which is exactly what §11.3(a) (every execution record ↔ exactly one valid receipt) and §11.3(c) (every `attestation_id` ↔ exactly one receipt and at most one execution) do. Failing closed in the interval is P-4 applied to storage: the ledger's answer is unknown, and unknown is never the permissive answer.

  *This is new normative text, not a restatement.* CL-3's indefinite origin-binding retention and CL-4's indefinite epoch retention are retention rules with no backup obligation behind them — rules about how long to keep a thing that nothing requires anyone to be able to recover. DP-39 supplies the obligation. It has no executable consumer: nothing in this repository restores anything.

- **DP-40 (NEW — this clause closes a live gap in ACP-SPEC-001, not a deployment question). The Executor's last-seen `bundle_epoch` MUST be durable and MUST be shared across every Executor instance in the tenant.** It **MUST** be held in the Consumption Ledger as a distinct per-tenant identifier class **alongside** those CL-3 enumerates, written and read under the CL-1 and CL-2 guarantees that govern a nonce, and **MUST** be read from there — never from process memory — at §9.3 step 4.

  *The allocation is taken openly, because taking it silently is the defect it is fixing.* CL-3 does **not** name this class, and adding it there is a revision of ACP-SPEC-001 that this document cannot make. Until that revision the class exists on this clause's authority alone, and a reader of CL-3 will not learn of it from CL-3. One artifact class enumerated in two documents is the CL-7 shape one register up, so it is disclosed here rather than presented as a reading of CL-3.

  *Why this is a defect in the specification rather than a deployment preference.* §9.3 step 4 requires `bundle_epoch` ≥ **the Executor's last-seen epoch**. The phrase "last-seen epoch" occurs **exactly once** in ACP-SPEC-001, at that step, and nowhere else. No clause makes the value durable, no clause makes it shared, and no clause says where it lives. CL-3's epoch class is scoped in its own words to "the high-water mark consulted by RAD-3" — the **KMS's** mark — and CL-4's indefinite retention attaches to that same KMS mark. So the specification obliges the Executor to compare against a value it never says how to keep. Meanwhile §14 suite 10 already demands "no epoch regression" **under concurrent Executors**: an executable obligation with no clause behind it, which is this repository's recurring defect running in the opposite direction and no less serious for it.

  *What breaks without it, stated as the attack.* An Executor holding the mark in process memory starts at zero. After any restart it accepts a **genuine**, correctly signed, more permissive **superseded** bundle at step 4 — and a second replica accepts one immediately, with no restart required at all. That is T-15, the defect RAD-3 was revised to close, reappearing on the side RAD-3 does not cover. The KMS's monotonic mark does not save it: RAD-3 constrains what the KMS will **sign**, and step 4 exists precisely because the Executor does not take the signing substrate's word for having got that right (A-6, TR-8). Nor does step 4's `policy_bundle_hash` check save it — a superseded bundle has a genuine hash and a genuine signature; being superseded is the only thing wrong with it, and the epoch mark is the only thing that knows.

  *Name the mutant, because a clause that cannot name one is documentation.* Replace the durable shared read at step 4 with a per-process counter initialised to zero, restart the Executor, and replay a receipt issued under the superseded bundle: the signature verifies, the proposal hash matches, the epoch clears a mark of zero, the action executes. **No suite in this repository kills that mutant today.** `reference/suites/conformance.py`'s `a_epoch_rollback` (T15) kills the in-process case by lowering the active bundle's epoch inside one live Executor. `reference/suites/bundle_suite.py`'s `t_restored_host_refuses_a_rollback_before_it_has_a_bundle` kills the adjacent bundle-host case, proving that a restored host carrying a mark refuses an older bundle before it has an active bundle. Neither restarts an Executor; neither runs two. No file under `reference/suites/` mentions an epoch under partition at all, so §14 suite 10's "no epoch regression under concurrent Executors" has no counterpart in the gate. The missing case is one test — two Executor instances over one ledger, with one instance restarted mid-sequence — and until it exists this clause is unenforced.

  *Where the reference stands, and why the reasoning was already available.* `reference/src/acp_executor.py`'s in-process `Ledger` initialises its epoch high-water mark to zero and raises under the id `RAD-3` — the KMS's clause — on regression. `reference/src/acp_ledger.py` does the same on the quorum-backed ledger the partition suites use, and holds the mark on the **wrapper**, outside the quorum object: the one place this repository models a replicated ledger is the one place the epoch mark is deliberately not replicated. The counter-example is `reference/src/acp_bundle.py`, where `BundleHost` takes `high_water` as a constructor argument and its `active_epoch` docstring argues that the mark must survive a restart with no active bundle, because "that window is the cheapest moment to serve a superseded bundle, so a host deriving its mark from what is serving has no mark at all." That argument is correct, it is already written down, and it was never carried across to the Executor.

  *Cost, stated plainly.* Step 4 becomes a ledger round-trip on every receipt, including the LOW/MEDIUM fast path EO-2 budgets most tightly. One relaxation is permitted and no other: a deployment **MAY** cache the mark in process **only as a monotone lower bound**, so that a cached value can cause a **refusal** and never an **acceptance**. Accepting still requires the shared read, because a cache sitting below the shared mark is exactly the stale value the attack uses. Stating the relaxation here rather than leaving it to implementers is deliberate — two normative requirements a deployment cannot satisfy at once is the DR-6 defect class, and DR-13 already set the precedent of resolving that in the text.

- **DP-41. The audit chain's constraints are a substrate specification and MUST be read as one.** AU-2 requires a UNIQUE `chain_hash`, a foreign key on `previous_hash`, `(tenant_id, seq)` UNIQUE **and gapless**, and inserts appended under `SERIALIZABLE` or a single-writer-per-tenant discipline. Accordingly, the following **MUST NOT** be used to hold the audit chain: an object store with eventually-consistent listing; any pipeline that can reorder, coalesce or duplicate writes — a log shipper, a batching agent, an at-least-once queue without deduplication on `(tenant_id, seq)`; and any multi-writer-per-tenant configuration that does not serialise.

  *What breaks without it, in both directions.* Gaplessness is what makes deletion detectable at all; a sequence with holes has no missing record, only a shorter one. Reordering breaks the chain link and is, at AU-4, indistinguishable from tampering — so a routine storage misconfiguration raises the critical integrity alert AU-4 exists to raise for a rewrite, and the second-order damage is worse than the first: operators who learn that the integrity alert usually means the log shipper stop reading it. AU-3's line applies to the substrate as much as to the anchor. An unanchored in-database chain is tamper-decorated rather than tamper-evident, and so is an anchored chain over a store that reorders.

  *Partially checked, and less than §14 suite 7 asks for.* `reference/suites/audit_suite.py` is in the per-commit gate and exercises AU-1 head derivation against the clause, AU-7 anchor-before-release ordering, post-anchor rewrite detection through reconciliation, and AU-8 genesis surviving destruction of a whole tenant chain. It does **not** contain the single-record tamper and reorder cases §14 suite 7 names; those remain a per-implementation obligation. Either way the evidence is about chain construction, and DP-41 is entirely about the engine the chain is written to, which nothing here observes.

- **DP-42. An audit commit is durable or it is not a commit.** Where the specification makes an audit write a precondition of an effect — AU-7's anchor-before-release for floor-HIGH, DR-13(1)'s notice-before-execution below floor-HIGH — the write **MUST** be durable before the effect is released. Acceptance by a buffer, a client-side batch, an asynchronous appender or an unflushed write-ahead log is **NOT** a commit for this purpose.

  *Rationale.* DR-13 buys detection rather than prevention, and the entire purchase is the durable local commit; AU-7 states the reasoning DR-13 borrows — "a record written after the fact can be suppressed by whatever the action enabled". A notice sitting in a buffer is suppressed by the same crash it was written to survive, and the irreversible action has already happened. The outcome is the pre-v1.3.15 state DR-13 exists to end: an IRREVERSIBLE, below-HIGH action executes leaving neither a human nor a record. Reaching that state through a storage configuration instead of a missing clause makes it no better, and makes it considerably harder to find.

  *Not checked, and the reason it cannot be mutation-tested is worth stating.* `reference/src/acp_executor.py` labels `record_notice` "the Executor's OWN durable state, deliberately" and implements it as a Python list. The reference models the **ordering** obligation and marks it as a mutation target — `DR-13-notice-before-execute` — so deleting the ordering check kills a mutant and the deletion is caught. Nothing kills a mutant for durability, because **durability is not a branch**. There is no line to delete; there is a guarantee the storage layer either provides or does not, and deletion mutants are blind to it by construction. That is a limit of this repository's strongest evidence method, disclosed here rather than papered over by relabelling an ordering test as a durability one.

- **DP-43. Every store in DP-35 MUST be partitioned per tenant, at the credential boundary.** A credential scoped to one tenant **MUST NOT** be able to read or write another tenant's rows in the Consumption Ledger, the audit chain store, the Bundle Repository or the Context Store.

  *This is not new; it is scattered, which is why nobody holds it.* D-1 requires dedicated per-tenant database schemas and per-tenant executor credentials, AU-1 makes chains per tenant, AU-2 keys uniqueness and gaplessness on `(tenant_id, seq)`, RAD-3's high-water mark is per tenant, CL-1 and CL-5 scope linearizability and ledger sharing per tenant, DR-12's unacknowledged-release counter is per tenant, and §9.3 step 8 refuses a receipt whose tenant does not match the credentials about to be used. Six clauses across five sections, none of which states the storage-layer obligation they jointly imply.

  *The drift, published rather than fixed quietly.* `docs/private/acp-deployment-architecture.html` — the artifact §2 of this document replaces — draws one undivided control plane and labels exactly one store "per tenant": the audit chain store. The Consumption ledger, the Bundle repository and the Context Store are drawn un-tenanted. That file is gitignored, so it sits outside `MANIFEST.sha256`, outside `tools/sync-counts.sh` and outside the clause-id assertion in `tools/selftest.sh`. Nothing in this repository could have caught the drift and nothing did, which is the argument for this document being where it is.

  *Partially checked, and narrower than it looks.* Step 8 is implemented in `reference/src/acp_executor.py`, but it compares the receipt's `tenant_id` against the **Proposal's**; the clause's subject is the **credential scope**, and the reference models no credential at all — the word does not occur in that file. §14 suite 3 lists a cross-tenant receipt as a required case, and no suite under `reference/suites/` constructs one. The storage-layer separation D-1 requires is observed by nothing here, in either language.

- **DP-44. Post-quantum signature expansion MUST be sized for in transport and in storage.** EO-2 records the expansion for a floor-HIGH receipt and states that it is **algorithm-bound**, does not improve with a faster library, and must be sized for. This document does not repeat the figure (DP-4): EO-2 is where it is stated, and a copy here would be a second definition of one value with nothing to reconcile them — precisely the drift that left the end-to-end latency bound stated three times in ACP-SPEC-001 with two of the three stale.

  *The storage consequence the specification does not draw.* AT-8 puts the **full** Attestation Object and the attester key into the receipt, one per attester, so a floor-HIGH receipt is not a fixed size: it grows with `quorum_k`. AU-5 then sets a retention floor for receipts and attestations measured in years. Floor-HIGH storage growth is therefore the per-signature expansion multiplied by the quorum and by the retention period, and it lands on the **audit store**, not on the ledger, which stores identifiers rather than signatures. A deployment that sizes the ledger for post-quantum receipts and the audit store for classical ones has sized both wrong, in the direction that fills up.

  *Not checked.* No command in this repository measures a stored receipt or an audit row, and nothing goes red if a deployment sizes for the classical figure. EO-2's own measurement is of verification latency and wire size, not of storage.

- **DP-45. The replica-count hole is named here and deliberately not filled.** No clause in ACP-SPEC-001 states a ledger replica count, a quorum size, or a failure-domain placement, and this document adds none. CL-5 names three acceptable substrates without sizing any of them; CL-6 and CL-7 presuppose a reachable majority without saying a majority of what. A deployment **MUST** publish its ledger replica count and the failure domains those replicas occupy, and **MUST NOT** cite this repository's partition evidence as evidence about its own topology.

  *What that evidence actually is.* `reference/suites/partition_suite.py` fixes `N = 5` as a module-level test parameter, and the exhaustive result — no two disjoint majorities across all subsets of that five-replica set, so CL-7's adoption is total rather than best-effort — is a property of **that fixture**. Five is not a normative floor, and the same suite makes the point itself by asserting that the set tolerating two failures must fail closed on the third rather than degrade.

  *Why it is not filled.* Choosing a number requires a failure model this document does not have and the specification declines to state: §4.2 excludes availability SLOs outright, and RES-2 is the reason it says so out loud rather than hiding behind the exclusion. Every fail-closed control routes to ATTEST, so a replica count chosen to reduce fail-closed events is a **safety** decision presented as a capacity one. Inventing one here would be new normative work wearing the costume of deployment guidance, which is the same reason §8 states almost nothing about backpressure.

  *Not checked, by construction.* This is a disclosure obligation on the deployment. Nothing in this repository reads a deployment's topology, and DP-45's own honest position is that the exhaustive partition result is the strongest evidence of its kind here and it is about five in-memory Python objects.

## 6. Cold Start and Boot Recovery (Normative)

**This section is new normative text and not a restatement, and the gap it fills is total.** ACP-SPEC-001 contains zero occurrences of *cold start*, *restart*, *reboot*, *boot*, *startup*, *start-up*, *graceful*, *drain* and *health*, and the two near-misses are unrelated: `initialization` appears once, at §9.1.1 step 1, where the KMS loads the `policy_signing_key` public key, and `readiness` appears once, in §1's v1.3.8 revision note about post-quantum readiness. The single crash-adjacent sentence in the whole specification is DS-2's "A crash between claim and completion yields no execution, never a duplicate" — which states an **outcome** and specifies no **procedure**. Nothing anywhere says what a component must re-read, re-verify, or refuse to do when it comes back.

That is not a cosmetic omission, because the specification names durable state in four places and specifies the recovery of none. An Executor that has stopped and started again holds, or has lost, all four: the last-seen bundle epoch of §9.3 step 4, the `pending_release` holds of DR-1, the notices DR-13 requires it to have committed, and the ledger claims DS-2 made before target calls whose outcome is now `indeterminate`. The reference bundle host already states the danger in code, about the analogous mark on its own side: the durable high-water mark "survives a restart with no active bundle; that window is the cheapest moment to serve a superseded bundle, so a host deriving its mark from what is serving has no mark at all" (`reference/src/acp_bundle.py`, `BundleHost.active_epoch`). Boot is the cheapest moment because at boot the component's memory agrees with an attacker about what has never happened.

**Terminology.** In this section a component **serves** when it accepts a Decision Receipt for verification under §9.3, releases a held action under §9.6, or performs any state change against an external target. Accepting a receipt in order to refuse it is not serving; accepting one in order to begin verifying it is. The distinction is stated because an unqualified "does not serve" is satisfied by a component that quietly queues work it will process the moment it stops refusing.

- **DP-46 (NEW — Normative). A component that cannot re-establish its durable state MUST refuse to serve, and MUST NOT start clean.** Before serving, a component **MUST** re-establish every item of durable state named in DP-47 through DP-50 that applies to it. Where any one of them is unreadable, unreachable, or of indeterminate contents, the component **MUST** refuse to serve for the affected tenant and **MUST** raise a critical alert. It **MUST NOT** initialise the missing value to a default, to zero, to empty, or to whatever the last reachable peer reports.

  *The branch that reads this default, named as RV-1 requires.* The reader is a refusal gate placed **ahead of §9.3 step 1**: with recovery incomplete, verification is not entered at all, so no receipt is ever evaluated against a partially reconstructed view. Placing the gate inside the checklist would be a second definition of fail-closed in a list that already has one, and it would leave steps 1–3 running against state steps 4–9 do not yet have. The shape exists in the reference on the bundle side — `BundleHost.read()` raises `Refused("NoActiveBundle")` rather than serving a member from nothing — and it is the shape, not a check on the Executor, which has no boot path in this repository at all.

  *Why starting clean is the exploitable case rather than the tidy one.* Every one of the four states is a record that something has **already happened**: an epoch was seen, a hold was entered, a notice was owed, a call may have landed. A fresh in-memory zero is indistinguishable from an honest deployment's first second of life, and it is precisely the state in which a superseded bundle looks new (DP-47), a held action looks unheld (DP-48), an owed notice looks discharged (DP-49) and a live target call looks unmade (DP-50). Fail-safe here means refusing, because the permissive reading of "no record" is the attacker's reading. P-4's rule that unknown is never LOW is the same rule one register up: unknown is never *fresh*.

  *RES-8 applies to recovery inputs, and this is where it would be missed.* Recovery values **MUST** be read from the component's own durable state or from the per-tenant Consumption Ledger (CL-1, CL-5). A component **MUST NOT** adopt a recovery value from a peer's status report, readiness probe, or health endpoint. A peer answering "the ledger is current" or "your notices were delivered" is a party certifying a security-determining value about itself to the component verifying it — the class that has recurred five times (C2 → X1 → Y1 → Z3 → W1) and the open shape of the notifier self-certification finding (**T-32** in **ACP-CLASS-001**). Boot is when this is most tempting, because the peer's answer is available and the durable read is slow.

  *Cost, stated plainly.* This clause makes a datastore outage at boot a total outage for the affected tenant, where a component that started clean would have appeared to work. That is the intended trade and it is the same one CL-2 and CL-6 already take at run time; stating it here only removes the exemption a restart would otherwise smuggle in.

- **DP-47 (NEW — Normative). The Executor's last-seen bundle epoch MUST be durable and MUST be shared per tenant.** The value compared in §9.3 step 4 **MUST** be held in storage that survives process and host restart, **MUST** be shared across every Executor instance in the tenant, and **MUST** be retained indefinitely. An Executor that cannot read it refuses to serve under DP-46. Sharing it in the Consumption Ledger satisfies this clause; CL-5's substrate list and CL-4's indefinite retention for epoch marks are the pattern, and no new store is required.

  *What breaks without it, named as a mutant.* Delete the durable read and the value defaults to the lowest epoch the process can represent. A genuine, correctly signed, more permissive bundle from a previous epoch then passes §9.3 step 4 unchanged — which is **T-15**, the bundle-rollback threat, rediscovered through a restart rather than through a replay. The same hole opens without a crash: a second Executor instance brought up to scale out begins life with a fresh mark, so scale-out and restart are one defect wearing two costumes. This is why the clause fixes durability **and** sharing together; either alone leaves the other path open.

  *This clause exists because §14 already tests it and nothing defines it.* Suite 10 requires "no epoch regression" under concurrent Executors and induced partitions. The phrase "the Executor's last-seen epoch" occurs exactly once in ACP-SPEC-001, at §9.3 step 4, and no clause makes it durable, shared or retained; CL-3's epoch class is scoped to "the high-water mark consulted by RAD-3", which is the **KMS's** mark and not the Executor's. So the specification carries an executable obligation with no clause behind it, which is the inverse of the defect §1 records three times — there, normative text with no executable consumer; here, an executable consumer with no normative text. Both are found by reading and neither is found by running.

  *Closest existing check, and exactly what it does not cover.* `reference/suites/bundle_suite.py` contains `t_restored_host_refuses_a_rollback_before_it_has_a_bundle`, which runs in the per-commit gate and asserts that a restored **bundle host** with a durable high-water mark of *n* refuses to activate epoch *n−1*. That is the RAD-3 analogue on a different component. It says nothing about the Executor's step-4 mark, and deleting this clause's obligation turns nothing in this repository red. The check that would is a restart case in the ledger suite; it does not exist.

- **DP-48 (NEW — Normative). Holds do not survive a restart: every in-flight `pending_release` action MUST be voided, audited, and returned to a fresh quorum.** An Executor **MUST** record entry into `pending_release` (DR-1) in durable state before the hold begins. On recovery it **MUST** enumerate every action still in `pending_release`, **MUST** void each one with a critical alert and an audit record, and **MUST NOT** resume, re-time, or release any of them. Consumed attestations remain consumed (DR-4): a voided action requires a fresh quorum, never a replay.

  *Rationale, and it is three separate reasons that happen to agree.* First, silence across downtime is not observed silence. DR-7 releases a `REVERSIBLE` action on silence because "the opportunity existed and was not taken"; while the Executor is down the opportunity did **not** exist, since DR-4/DR-5 repudiations are accepted by the Executor and a repudiation submitted into a dead process is lost. Releasing on that silence would be counting an outage as consent, and DR-8's rule — executing while the detection channel is absent is executing unwatched — is the same objection stated for delivery. Second, the elapsed hold cannot be measured across a restart, for the reason DP-52 gives. Third, DR-9 already fixes the disposition of a hold whose window ran out without an answer: timeout fails closed and requires a fresh quorum. A restarted hold is analytically a timed-out one, so this clause is DR-9's disposition applied to an interruption DR-9 did not name rather than a new rule.

  *Why the clause is needed when DR-6 appears to force it anyway.* DR-6 caps the hold below receipt validity (L-28, L-14), so after a long outage the receipt has expired and release fails closed regardless. That covers the slow case and leaves the dangerous one open: a restart completing inside the receipt's remaining validity produces a hold that is still formally releasable, having been unwatched for part of its window. A rule that only bites when something else already bit is documentation, so this clause is written to bite where DR-6 does not.

  *Cost, stated plainly.* A rolling restart across Executor instances voids every in-flight floor-HIGH hold in the tenant and converts each into fresh human quorum work. That is real load landing on the mechanism RES-2 and AT-7 identify as the one that degrades under load — a flooded quorum converges to rubber-stamping — so an ordinary deployment operation composes into a safety-relevant pressure. Deployments **SHOULD** drain `pending_release` to empty before a planned restart and **MUST** alert on the count voided by an unplanned one. This is disclosed rather than resolved: no clause here caps that load, and capping it would mean releasing something unwatched.

- **DP-49 (NEW — Normative). Notices committed and not yet delivered MUST survive the restart that separates them from delivery.** The DR-13 notice backlog — notices durably committed before execution but not yet delivered — **MUST** be held in storage that survives restart, and on recovery the Executor **MUST** re-enumerate it and resume delivery attempts and reconciliation before serving the affected action classes.

  *What breaks without it.* DR-13's precondition is the durable local commit, and it discloses the residual plainly: "a notice committed and never delivered leaves an audit record and no human." It then places two MUSTs on the deployment — reconcile committed notices against delivery outcomes, and alert on the undelivered backlog. A backlog lost at restart makes both of those unsatisfiable **silently**: reconciliation finds nothing outstanding, the alert stays green, and the disclosed temporary residual becomes a permanent one for every notice in flight at the moment of the crash. The failure has the shape DR-12 warns about — silence that stops being measurable is no longer debt, it is just absence.

  *A limit worth stating rather than smoothing over.* This clause preserves the obligation; it does not make delivery a precondition of anything. DR-13 deliberately keeps delivery asynchronous for the EO-2 reason, so an Executor that recovers its backlog and still cannot deliver has satisfied this clause and left the residual exactly where DR-13 put it.

- **DP-50 (NEW — Normative). Ledger claims whose target outcome is unknown MUST be enumerated before serving the affected action class.** DS-2 requires the ledger identifier to be claimed before the target call, so a crash between the two leaves a claim in the ledger and no recorded outcome. On recovery the Executor **MUST** enumerate every such claim for the tenant, **MUST** record each as `indeterminate` per EX-2, and **MUST** hand each to the DS-3 reconciliation procedure before serving the corresponding action class.

  *Why this adds no store and only names an obligation.* The evidence already exists — DS-2's ordering is what puts it in the ledger rather than in process memory, and that ordering was chosen so a crash yields no execution rather than a duplicate. What the specification never says is that anyone must go and look after the crash. DS-3 defines the reconciliation procedure but names no trigger, no owner and no bound on how long an `indeterminate` may sit undetected; §11.3(f) only says the job surfaces them. Boot is the one moment at which the set of unresolved claims is both knowable and small, and a deployment that serves before looking has silently converted DS-3's "may be dropped" into "was dropped, and nobody counted."

  *Residual.* This clause bounds *detection* at boot. It does not bound detection during normal operation, where DS-3's missing interval remains missing, and it does not make the reconciliation correct. It also assumes the claim record identifies the action class, which DS-6a's `action_id` supports and which no clause in ACP-SPEC-001 requires the ledger to expose.

- **DP-51 (NEW — Normative). Recovery MUST NOT re-issue from a stored receipt.** Where recovery determines that an authorized action was not executed, or may not have been, the Executor **MUST NOT** replay, re-present, or re-issue any stored receipt. The action **MUST** be re-driven through a **new attestation** per DS-3, bounded by DS-6e, and the target idempotency key **MUST** be derived from the ledger-pinned `proposal_hash → origin_nonce` binding per DS-6f — never from any value the re-drive receipt carries, which is diagnostic only and, if present and disagreeing with the ledger, is a critical alert.

  *Why this clause exists when DS-3 and DS-6f already say it.* Because boot recovery **is** the path those clauses were written about, and nothing connects them to it. DS-6's Y3 rationale is the sentence to read twice: the duplicate-prevention mechanism "was disabled precisely and only in the recovery path built to cope with lost outcomes." A boot runbook is that recovery path, written by an operator under pressure who has a valid stored receipt in front of them and an action that appears not to have run. The naive move — re-present the receipt, it is still signed, it is still inside its window — is the dangerous one, and for floor-HIGH non-idempotent targets it is the doubled trade or the doubled actuator command DS-4 names as the worse failure. The nonce is single-use (CL-3, T-09), so the naive move mostly fails closed; the case where it does not is a re-drive whose key moves because the origin was taken from the receipt rather than the ledger, which is Z3.

  *This clause specifies no mechanics.* DS-3, DS-6b, DS-6e and DS-6f define them, and restating them here would be the encoding-split defect the PB-8 and AU-1 corrections were both about. It binds boot to them and does nothing else.

- **DP-52 (NEW — Normative). Durations MUST be measured on a monotonic clock; instants MUST be evaluated against NTS-disciplined wall time.** The `hold_window` of DR-1 is a **duration** and **MUST** be measured against a clock that does not step. The receipt's `issued_at` and `expires_at`, and the skew allowance, are **instants** and **MUST** be evaluated against the NTS-disciplined wall clock A-2 and §12.5 require, within L-20's allowance. A component whose monotonic clock is not continuous across the interval being measured — which every process restart guarantees — **MUST NOT** treat the interval as measured; under DP-48 the hold is voided rather than re-timed.

  *Rationale.* ACP-SPEC-001 uses `monotonic` of bundle epochs, of the ledger, of audit sequence numbers and of risk under rule extension — **never of a time source** — and it contains no occurrence of *wall clock*. So the two kinds of time it depends on are undistinguished, and the same clock read serves both. That is what makes the restart case ambiguous: an Executor that resumes a hold by comparing two wall-clock timestamps has measured an interval across an event that can move the clock.

- **DP-53 (NEW — Normative Disclosure). A wall-clock step during a live hold is an open hole and is NOT CHECKED.** DP-52 fixes which clock measures what. It does not eliminate the case where the wall clock steps **during** a hold that is otherwise proceeding normally. Because the hold is a duration and receipt expiry is an instant, a backward step can leave the receipt live while the Executor believes less time has elapsed, and a forward step can expire the receipt mid-hold. The second outcome is DR-6's failure exactly — "a 60 s hold inside a 60 s receipt window expires mid-hold and never releases the honest path" — which that clause records as having been found by testing rather than by reasoning. Deployments **MUST** treat a detected step exceeding L-20's allowance during a live hold as a fail-closed condition for that hold and **MUST** alert on it.

  *Why this is disclosed rather than solved.* Solving it means specifying the Executor's behaviour when its own time source is lost, and §12.5's remedy — cap Decisions at ATTEST — is a Policy-Engine action that names nothing for a verifier that issues no Decisions. Writing that remedy here would be new normative work on a component boundary this document does not own, so the hole is named and left open rather than closed by assertion.

  *Coverage, stated rather than implied.* No test in this repository steps a clock during a hold, and none could without a boot path to step it in. This clause is an obligation on a deployment and an instruction to an auditor. It is not evidence.

**Coverage of this section, before anything it claims.** Nothing in this repository boots — no service has a startable entry point (ACP-63) — so **every clause DP-46 through DP-53 is recorded NOT CHECKED in §9's table**, and none of them is credited to an existing gate. The one adjacent check, `bundle_suite.py`'s restored-host case, covers the bundle host's RAD-3 mark and is named under DP-47 with its scope stated so it cannot be read as covering the Executor. The check that would make DP-47 a control is a restart case in the ledger suite (§14 suite 10) asserting that a restarted Executor refuses a superseded bundle epoch; the check that would make DP-48 one is a case asserting that an action in `pending_release` at shutdown is voided and not released. Until those are written, this section is a specification of an obligation and not a demonstration of one, and it should be read the way §14 suite 11 asks the rest of the document to be read.

## 7. Degraded Mode and Dependency Loss (Normative)

**Read the heading as a warning, not as a promise.** ACP-SPEC-001 contains the word *degraded* zero times, and this section does not introduce the concept the heading appears to name. There is no mode in which a component keeps authorizing or keeps executing at reduced assurance. What follows enumerates the dependencies whose loss **stops** something, and states exactly what it stops.

The section is uneven and the unevenness is the point. Five losses are already specified in ACP-SPEC-001; they are **cited** below and deliberately not restated (DP-57). At least five are specified nowhere, and DP-58 through DP-62 state them for the first time. Those five are **new normative text**, not a reading of the specification, and none of them has an executable consumer anywhere in this repository. Where that is true it is written into the clause rather than left to the register in §9, because a reader who stops at this section should not leave it believing more is checked than is.

Re-establishment *after* a dependency returns — what a component must re-read and re-verify before it serves again — is §6 of this document, not this section. This section is about the loss, not the recovery.

- **DP-54. There are exactly two sanctioned responses to dependency loss, and continuing is not one of them.** A component that loses a dependency **MUST** either fail closed, or — where the clause governing *that* dependency says so, and only there — cap new Decisions at ATTEST until the dependency is restored, subject to attestation-queue rate limiting (AQ-2). It **MUST NOT** serve on reduced assurance, and no clause in this document creates a third response.

  *Why the two are not interchangeable.* Capping at ATTEST is not the gentler option; it is a different one, and choosing it where a refusal was required converts an availability event into a safety event. Every fail-closed cap routes work into the human quorum, and a flooded quorum converges to rubber-stamping (AT-7) — the induced-fail-closed composition disclosed as RES-8's neighbour in §15 (RES-2), which §8.6a exists to mitigate and explicitly does not eliminate. The anchoring-outage rule (AU-6) is the specification's own worked example of the conversion: an attacker denying the anchor service otherwise forces every action through quorum *and* acknowledgement at once, which is why AU-6 carries the W2 sub-rule at all. An availability attack that manufactures approver fatigue is a safety attack with one extra step.

  *Why there is no third response.* An availability SLO is explicitly out of scope (§4.2), so no clause in this document may trade assurance for uptime — there is no budget defined to spend. A deployment that needs an action to survive a dependency outage must change the dependency, not the response.

  *Conformance status.* No command in this repository goes red when this clause is violated. It is a rule about the shape of every clause below it, and the checks that exist test individual clauses, never their uniformity.

- **DP-55. Cached, stale or best-effort dependency state MUST NOT be substituted for a live read.** Where a dependency is unavailable, a component **MUST NOT** proceed against a cached copy, a replica known to be beyond its staleness contract, or a last-known-good value, unless the clause governing that dependency permits it explicitly and bounds it.

  *Rationale, and it is the field-and-relation audit's own example.* The conformance obligation to classify every control input **R**, **B** or **T** (§14 suite 12) already names this substitution as the way an implementation acquires a class-**T** input the specification does not have — "by caching a bundle rather than re-reading it" is the example the clause gives — and any unlisted **T** is a conformance failure. The substitution is therefore not a local performance decision; it silently changes the deployment's classification table, and the table is what §14 says must be re-derived against the build rather than inherited from this text.

  *What breaks without it.* Nothing visible. A cached read and a live read produce the same bytes on the wire, the same audit record, and the same green suite run; the difference appears only in the window where the cached value is wrong, which is exactly the window an attacker who can deny the dependency chooses. That invisibility is why this is stated as a prohibition rather than as guidance.

  *The permitted case, so the prohibition is not read wider than it is.* The Context Store is permitted a read replica under a staleness contract (§8.7, §8.7.1). A bound is not a licence to exceed it: beyond the contract, §8.7 already fails closed, and this clause adds nothing there.

  *Conformance status.* No command in this repository goes red when this clause is violated. No component here caches a bundle, so there is no branch to delete and no mutant to kill.

- **DP-56. Capping at ATTEST is an issuance-side response only.** The ATTEST cap is available to components that issue Decisions — the Policy Engine, and the signing substrate acting on the issuance path (RAD-2). It is **not** available to a component that verifies a Decision someone else issued. The Executor issues no Decisions; it trusts a signature, not a channel (§9.1). A deployment **MUST NOT** specify an ATTEST cap as an Executor-side remedy for any dependency loss.

  *What breaks without it.* An ATTEST cap written for the Executor is unimplementable, and the failure mode is that it is implemented as nothing while remaining written down. The deployment then has a documented remedy for a real outage, no code behind it, and no test that could tell — which is the shape this repository keeps finding in itself and the reason §9 of this document exists.

  *This clause is a precondition for DP-64,* which is what the Executor's missing remedy actually is.

  *Conformance status.* No command in this repository goes red when this clause is violated.

- **DP-57. The five dependency losses ACP-SPEC-001 already specifies are cited here, never restated.** A deployment **MUST NOT** derive behaviour for these five from this document. The normative text is in ACP-SPEC-001; this table is a citation index and a coverage disclosure.

  | Dependency lost | Specified response | Governing clause | What in this repository goes red |
  | --- | --- | --- | --- |
  | Consumption Ledger unavailable, or unable to confirm absence | fail closed | ledger claims and partition behaviour (CL-2, CL-6) | `partition_suite.py`, in the per-commit gate — the refusal is asserted by name |
  | Context Store unreachable or beyond staleness bounds | fail closed; DENY with a distinct reason code | Context Store integrity (§8.7) and the default-DENY rule (P-4) | **nothing** |
  | Notification undeliverable on the deferred path | the action does not release | undeliverable notification (DR-8) | `conformance.py`, in the gate — two cases |
  | External anchoring unreachable | chain internally, cap new Decisions at ATTEST subject to AQ-2, and either suspend sampled confirmation (DR-10) or fail closed for the tenant | anchoring outage (AU-6, closing W2) | `audit_suite.py`, in the gate, with a deletion mutant on the sampling suspension |
  | Time source unavailable | cap Decisions at ATTEST until restored, subject to AQ-2 | time synchronization (§12.5) | **nothing** |

  *Why this document does not repeat the obligations.* Two statements of one rule is the encoding-split defect the AU-1 (§11.2) and PB-8 (§8.2) corrections were each about, and both survived a full release cycle because prose drifts silently. A citation that goes stale is a broken link, which a reader notices; a paraphrase that goes stale is a second normative rule, which nobody does.

  *They are not uniform, and the non-uniformity is not an oversight.* Three fail closed and two cap at ATTEST. *Offered as a reading and not as a new rule:* the three that fail closed each remove a control on the **specific action being decided** — its single-use guarantee, the operator's capability, the detection channel that would notice it. The two that cap remove a **system-wide evidentiary property** — tamper-evidence, clock discipline — that does not make any individual action unauthorized, so refusing everything would be a self-inflicted outage while routing to human quorum keeps a human present. That reading is not stated anywhere in ACP-SPEC-001 and a deployment must not act on it; it is recorded so that the next clause added to this family has a criterion to argue against rather than a coin to flip.

  *Two of the five rows have no executable consumer, and the row's presence in ACP-SPEC-001 is not evidence any implementation obeys it.* No suite exercises a Decision refused because the Context Store was unavailable — P-4's distinct reason code for that case has no branch under test — and nothing at all exercises the NTS-loss cap. Both are normative MUSTs today, in the released specification, checked by nobody.

  *Conformance status.* The suites named above catch violations of the **cited** clauses. Nothing catches a violation of DP-57 itself — a restatement here that drifts from what it cites — which is precisely the defect the clause exists to avoid and precisely the one the AU-1 correction was.

- **DP-58 (NEW in this document — Normative). An unreachable signing substrate propagates DENY, and MUST NOT cap at ATTEST.** ACP-SPEC-001 specifies the KMS **refusing** — `SIGNING_DENIED` with a critical alert and a DENY propagated by the Policy Engine (§9.1.1 step 7), and rejection of all signing requests until a valid bundle is presented (RAD-4). Neither covers the KMS being **absent**. Where the signing substrate is unreachable, the Policy Engine **MUST** reach the same terminal outcome as §9.1.1 step 7 — DENY with a critical alert — and **MUST NOT** cap the tenant's Decisions at ATTEST.

  *Why ATTEST is the wrong answer here specifically.* ATTEST is not a route around the KMS. An attested Proposal still requires a receipt and a receipt requires the KMS to sign (§9.1.1 step 6), so capping during a signing outage does not defer the work — it spends the quorum's attention on a queue that will fail closed when the humans finish. That is the RES-2 composition reached by a different road, and it is worse than the plain refusal because the deployment believes it is degrading gracefully.

  *What this clause does not specify, deliberately.* No retry, no backoff, no timeout, and no circuit-breaker state. Those are transport concerns and specifying them here would put an availability policy inside a control decision. The clause fixes only the terminal outcome: whatever transport-level recovery a deployment adds **MUST** end in DENY, never in a cap and never in an ALLOW derived from a cached prior signature.

  *Conformance status.* No command in this repository goes red when this clause is violated. Nothing here boots and no service `main()` returns zero, so there is no KMS to be unreachable.

- **DP-59 (NEW in this document — Normative). An unavailable Attestation Presentation Service is an outage, and MUST be left as one.** Where the presentation service is unavailable, floor-HIGH Proposals awaiting attestation **MUST** remain unattested and **MUST NOT** be released. A deployment **MUST NOT** substitute an alternative renderer, a plain-text fallback, or a direct display of the canonical bytes by any other component.

  *Why the substitution is the danger and the outage is not.* The presentation service is TCB (§4.3) and A-8 concedes that its compromise defeats the quorum; the fixed-template rendering rule (AT-3) and the rendering-path distinctness rule (DR-2) are what bound that concession. A fallback renderer doubles the TCB: two components can now display a proposal to approvers, so A-8's single compromise has two doors, and the deployment's DR-2 distinctness argument must hold against both — which nobody re-derives for a component that exists only during an outage and is exercised only when attention is elsewhere. DR-2 already states that independence must hold under compromise and not merely in the nominal case; a fallback is the nominal case by construction.

  *The honest cost.* This clause buys nothing and costs availability. It is a prohibition, not a mitigation, and the correct posture during the outage is to have no floor-HIGH throughput — which §4.2 permits, because availability is out of scope, and which DP-54 requires, because the alternative is assurance traded for uptime.

  *Conformance status.* No command in this repository goes red when this clause is violated, and the reason is worth stating rather than glossing: there is no presentation *service* here to be unavailable. `sim/approve/render.py` is in-process, so the outage this clause governs cannot be induced.

- **DP-60 (NEW in this document — Normative). An unreachable Bundle Repository fails closed on every consumer.** Where the Bundle Repository is unreachable, the KMS **MUST** reject signing requests, and the Policy Engine and the Executor **MUST** fail closed rather than evaluate or verify against a stored copy of the bundle.

  *The seam this closes.* RAD-4 requires the KMS to reject when it cannot cryptographically verify the bundle it consults. An unreachable repository is not a verification failure — it is the absence of an artifact to verify — and the specification distinguishes the two nowhere. Stating one terminal outcome for both is deliberate: leaving them different is exactly the gap in which a cached copy looks like the reasonable engineering answer.

  *What breaks without it.* DP-55's manufactured class-**T** input, at the worst location in the system. The bundle is the right-hand side of every recomputation the architecture depends on: floor-only risk (TR-8), reversibility (RV-3), the quorum threshold (PB-6), the notice recipient set (DR-13(2)), the attester registry (PB-7). A verifier recomputing against a copy whose currency it cannot establish satisfies the recompute discipline in form and defeats it in substance — RES-8 with the recomputation still present, which is harder to see than RES-8 with it absent.

  *One permission that is not this.* In-flight evaluations complete under the bundle they started with (PB-3). That is a completion rule for work already admitted, not a licence to admit new work against a stored copy, and this clause does not disturb it.

  *Conformance status.* No command in this repository goes red when this clause is violated.

- **DP-61 (NEW in this document — Normative). An audit store that is unavailable or failing writes is a TOTAL EXECUTION OUTAGE, not a logging fault.** Where the audit store cannot accept a durable write, execution **MUST** stop — for every action, at every risk grade — and the condition **MUST** be treated and alerted as an execution outage.

  Two independent obligations produce this, one on each path:

  1. **Below floor-HIGH.** The notice of an IRREVERSIBLE action must be committed to the Executor's own durable audit state *before* the action executes, and executing ahead of the committed notice fails closed (DR-13(1)). A store that cannot accept the write cannot satisfy the precondition, so every IRREVERSIBLE below-HIGH action stops.
  2. **At floor-HIGH.** The audit record of the Decision must be covered by an external anchor before release, and release fails closed otherwise (AU-7). A record that was never written cannot be anchored. The chain's own integrity constraints (AU-2, gapless per tenant) independently forbid proceeding past a failed insert and resuming afterwards.

  *Why this needed saying, and it is the sharpest consequence in this section.* No reader of ACP-SPEC-001 would predict it. §9.6 reads as a notification section and §11 reads as an evidence subsystem; neither mentions availability, and neither says that losing the audit database stops the business. The consequence is arrived at by composition, and it arrives on the **fast** path — the bulk of a deployment's traffic — through a v1.3.15 clause whose text is about visibility. That is a significant operational property of DR-13 that the specification never states, and it is stated here as **new normative text** rather than as a reading of DR-13, because DR-13 does not say it and this document must not pretend to be quoting.

  *The tempting violation, named so it can be refused by name.* Buffering audit records in volatile memory to keep executing while the store is down satisfies the letter — a commit happened — and voids the reason. DR-13(1) gives that reason itself: a record written after the fact can be suppressed by whatever the action enabled. A record that dies with the process is a record written after the fact with extra steps. Durability is the property; the successful write is only its evidence.

  *Conformance status, with the missing mutant named.* No command in this repository goes red when this clause is violated. `conformance.py` exercises DR-13's notice commit on the positive path and its no-recipients refusal, both in the gate, but the reference's notice store cannot fail, so the branch this clause governs is untested. The mutant that does not exist: move the notice commit to *after* execution and assert that a below-HIGH irreversible action then executes with no durable record. Until that case is written, DR-13(1)'s ordering is a positive-path obligation on this branch and not a demonstrated control.

- **DP-62 (NEW in this document — Normative). A notification service that is down is distinct from a delivery that fails, and on the fast path it stops nothing.** Undeliverable notification (DR-8) governs a delivery that is attempted and fails or reaches no one. This clause governs the service being absent. On the deferred path the two collapse and DR-8 applies unchanged: no reachable recipient is no reachable recipient, and the action does not release. On the DR-13 fast path they do **not** collapse — actual delivery is not a precondition of execution there — so a notifier that is entirely down stops nothing at all. Where the notification service is unavailable, a deployment **MUST** raise the undelivered-notice backlog alert that DR-13 already requires, and **MUST NOT** infer from an absence of delivery *failures* that delivery is occurring.

  *What breaks without it.* Precisely the residual DR-13 discloses — "a notice committed and never delivered leaves an audit record and no human" — sustained for the length of the outage, across the path that carries most of the traffic, with the fast path running at full rate throughout. The deployment is executing unwatched in DR-8's sense while every DR-8 check passes, because DR-8 is not on this path. The second half of the clause is the one that matters operationally: a naive counter cannot distinguish "no failed deliveries because the channel is healthy and idle" from "no failed deliveries because nothing was attempted", and an outage that produces silence rather than errors is the one that lasts.

  *This document does not close DR-13's residual; it names where the residual becomes an outage.* DR-13 already requires deployments to reconcile committed notices against delivery outcomes and to alert on the backlog. That obligation exists and is unimplemented here.

  *Conformance status.* No command in this repository goes red when this clause is violated. There is no undelivered-backlog reconciliation in this repository — no implementation and no test — so the alert this clause depends on does not exist to be suppressed.

- **DP-63 (NEW in this document — Normative). A health or readiness report MUST NOT be a control input.** A component's own report of its dependency status — a health endpoint, a readiness probe, a status field on a response, a delivery flag — **MUST NOT** reach any branch in another component that decides whether an action executes. A consumer establishes a dependency's state from its own failed operation against that dependency, or from bytes signed by a party it already trusts.

  *Rationale (RES-8), and this one is open right now in exactly this shape.* The Executor learns the ledger is unavailable because its own compare-and-swap claim did not succeed (CL-2), not because the ledger said so. A component reporting "ledger reachable" or "anchor current" to its verifier is a party certifying its own dependency status to the party verifying it — the class this architecture has hit five times, each time inside the machinery the previous fix introduced (C2 → X1 → Y1 → Z3 → W1). The notifier self-certification finding (**T-32**, allocated in **ACP-CLASS-001**) is the live instance: `note.source_path`, `note.from_canonical` and `delivered` are all classified **T** for this reason, and splitting the codebases did not move them, because the Executor still reads them from the party it is verifying.

  *What this does not forbid.* Health endpoints for orchestration — restarting a container, removing an instance from a load balancer, paging a human — are operational plumbing and are untouched. The prohibition is narrow and exact: the value must not reach a branch that gates execution.

  *And naming it here does not make it compliant.* Under the field-and-relation audit (§14 suite 12) a status field that does reach such a branch is a class-**T** input, and every **T** must be enumerated against a disclosed residual or it is a conformance failure. This document enumerates none, so a deployment that permits such an input must enumerate it in its own table; citing DP-63 is not enumeration.

  *Conformance status.* No command in this repository goes red when this clause is violated. The classification obligation it leans on is per-implementation by construction, and this repository ships no table for a deployment.

- **DP-64 (NEW in this document — Normative). An Executor that loses its disciplined time source MUST fail closed.** Time synchronization (§12.5) binds "all receipt-issuing and verifying components" and gives one remedy — cap Decisions at ATTEST until restored, subject to AQ-2 — which is issuance-side. A verifier issues no Decisions (DP-56), so the Executor is inside the MUST and outside the remedy. Where a receipt-verifying component's time source is unavailable or its skew cannot be bounded, it **MUST** refuse.

  *The hole, stated narrowly rather than dramatised.* Three verification obligations read the Executor's clock: the freshness and window-length check (§9.3 step 5, whose Executor-enforced window *length* is what closed Y2), the hold before release (DR-1), and the requirement that the receipt outlive the hold (DR-6). An Executor with an undisciplined clock can perform all three and have none of them mean anything, while every audit record it writes looks correct. Nothing in the specification tells it to stop.

  *Why a narrow hole still earns a clause — this is the RV-1 test.* It changes no outcome in a deployment whose time source is healthy, and a clause that changes no outcome is documentation rather than a control. The branch it names is the refusal itself: without it, an implementer reading §12.5 finds an obligation with no consequence attached at the verifier and reasonably concludes the verifier is out of scope. That is the shape RV-1 had for four releases — a rule that set a value nothing below the floor-HIGH gate ever read — and DR-13 is what gave it effect. This clause is the equivalent, stated at the point the omission is visible.

  *A second hole this clause does **not** close, disclosed rather than quietly narrowed.* Neither ACP-SPEC-001 nor this document distinguishes a monotonic source from wall time for measuring the hold (DR-1), while the receipt's expiry (DR-6) is an instant on a wall clock. A wall-clock step during the hold either releases early or expires the receipt mid-hold, and the second is the DR-6 failure that testing found once already on an unrelated path. Fixing it is an amendment to DR-1 and DR-6 in ACP-SPEC-001, not a deployment obligation, so it is recorded here as an open defect and left open.

  *Conformance status.* No command in this repository goes red when this clause is violated. Nothing exercises the §12.5 cap on the issuance side either — see DP-57's table — so the whole time-source family is normative and unchecked in both directions.

**Coverage of this section, stated before anyone infers it.** Eleven clauses, and not one of them has a check that would go red on its violation. DP-57's table names three existing suites, but those suites catch violations of the clauses DP-57 *cites*, not of DP-57 itself. Five of the eleven (DP-58 through DP-62) are new normative text with no consumer in any language, and DP-61 is the one whose absence would cost a deployment the most. §9 of this document carries the register; this paragraph exists so that the register cannot be the first place a reader learns it.

## 8. Backpressure and Capacity (Normative, with an Open Problem)

This is the shortest normative section in this document, and the length is the finding rather than an accident of drafting. Almost nothing about capacity can be required here without inventing policy on top of an interaction that ACP-SPEC-001 records as **unanalysed**. So this section states one prohibition, one refusal, and one rule about what a deployment may publish, and then stops.

**The gap, evidenced.** ACP-SPEC-001 contains no backpressure model. Word-boundary searches over `spec/ACP-SPEC-001.md` return zero hits for `backpressure`, `back-pressure`, `shed`, `throttl`, `buffer` and `spill`; `overflow` returns two hits and both are arithmetic obligations inside the Annex B Dafny artifact, not queue behaviour. What does exist is detection and only detection. Queue-depth monitoring (AQ-3, §8.6a) requires depth and arrival rate per attester to be monitored and makes depth beyond a configured bound *a critical alert, not a silent backlog*; the limits table carries the same bound as a bundle-configured value whose enforcement point is AQ-3 (L-23). Neither states any behaviour **at** the bound. An alert says a queue is too deep. It is not a policy for what happens next, and the specification does not have one.

- **DP-65. Attestation items MUST NOT be discarded to relieve queue pressure.** An item awaiting attestation **MUST** leave the queue only through an outcome ACP-SPEC-001 already defines: an attestation reached, voiding under the re-evaluation on quorum (AT-4), which returns the Proposal to disposition, or expiry, which is void (AT-5) and therefore fails closed. It **MUST NOT** be discarded, sampled out, spilled to another store, aged out short of expiry, or demoted to a lower-priority queue on the strength of depth, arrival rate, or capacity pressure of any kind.

  *Rationale, and it has two halves.* The first is that a drop defeats the instrument that would report it. Queue-depth monitoring (AQ-3) measures depth, so deleting items to reduce depth resolves the alert by deleting the thing the alert measures: the line goes green while the backlog it was watching has been converted into authorized actions that no human ever saw. This repository already states the general rule against that move — a finding is never resolved by retuning the thing that found it — and a shed policy is that move applied to a human control.

  *Why the prohibition is total, and not the weaker form.* The obvious clause here is "**MUST NOT** be *silently* dropped", and it is the wrong clause: it licenses a **loud** drop, which is a shed policy with an audit record, and DP-66 declines to specify one. A clause permitting what the next clause refuses to define is the DR-6 defect class — two requirements a deployment cannot jointly act on — so the prohibition is stated at full strength and overflow resolves through the mechanism the specification already owns. Expiry is void, and void fails closed. An item lost to expiry is a refused action, not an unwatched one.

  *What this does not do.* It does not bound the queue, and an unbounded queue whose items expire is a liveness failure. That trade is deliberate and it is the same one the ledger makes under partition, where a burned receipt is the documented liveness cost of failing closed (CL-6). This section prefers a visible liveness failure to an invisible safety one, and says so rather than presenting the choice as free.

- **DP-66. This document specifies no overflow policy, and the omission is a refusal rather than an oversight.** No drop, shed, spill, sample, priority-demotion or admission-control policy for the attestation queue is specified here. A deployment **MUST NOT** read that absence as license to select one at will: such a policy changes the safety argument and belongs in a revision of ACP-SPEC-001, subject to its release-integrity rule, not in a deployment document.

  *Why, first reason.* Every candidate policy lands directly on a composition the specification discloses rather than solves. Every fail-closed control routes to ATTEST, and a flooded quorum converges to rubber-stamping, silently converting floor-HIGH into effective-ALLOW — the induced fail-closed residual (RES-2, §15), which states that queue partitioning and rate-limiting *mitigate* the composition and do not eliminate it. The behavioral-assumption warning (AT-7) then concedes the part that matters here: if attesters converge to rubber-stamping there is **no mechanical fallback**. A capacity policy over that queue is therefore a safety control wearing an operations label, and writing it here would be the wrong document, the wrong review, and the wrong version bump.

  *Why, second reason, and it is the decisive one.* The interaction such a policy would have to reason about is recorded as **Open**. Whether the cap-escalation marking (AQ-2) creates an adversary-influenceable channel — an attacker who can trip a fail-closed control thereby influences which queue an item lands in — and how AQ-2's rate-limiting interacts with floor-HIGH queue priority, is listed in §15's open problems and dispositioned in Annex C as *"Open. Added to §15 open problems. Not yet analysed."* (X2). Specifying an overflow policy on top of an unanalysed interaction would be new normative work presented as deployment guidance, and that disguise is what makes such a change hard to review. This section cites X2 and adds nothing to it.

- **DP-67. A deployment MAY publish a measured or operational availability target, and MUST NOT present one as a requirement of ACP-SPEC-001 or of this document.** Availability is explicitly out of scope: §4.2 specifies no availability SLO. Where a target is published, it **MUST** carry §4.2's own accompanying note — that denial of service is not fully severable from safety, per the induced fail-closed residual (RES-2) — because a number published without it invites the reading that meeting the number discharges the safety concern. It does not: the failure mode is not the system stopping, it is the system continuing while its human control degrades.

**A correction worth recording, and this section is where it surfaced.** The §4.1 threat table names the countermeasure for induced attestation flooding (T-17) as *"Queue isolation (§8.6a) + ES-6 monitoring"*. `ES-6` is defined nowhere. It occurs exactly once in ACP-SPEC-001 and exactly once in the whole repository — that cell — and there is no `ES-` clause family at all. This section found it by writing, because T-17 is precisely the threat a capacity section cites, so the citation this section would naturally have made is a citation of a promise with nothing behind it. It is unfalsifiable in the `CL-7` way, inverted: `CL-7` was one id naming two rules, so a claim of "CL-7 satisfied" could satisfy either and cite the clause honestly, whereas this is one id naming zero rules, so no implementation can satisfy or fail "ES-6 monitoring" and no conformance claim about T-17's mitigation means anything. Nothing in the repository could have caught it by running: the clause-id uniqueness assertion reports ids defined **twice** and is blind by construction to an id defined **never**. The disposition is a specification-side action this document cannot take — define ES-6, or strike the promise from T-17's countermeasure column and publish the removal as a correction. Adding it to an exception list to keep the dangling-clause-id check registered in §9 green would be resolving the finding by retuning the instrument that found it, and is not available. The finding is filed rather than reported only here.

**Conformance status of this section (Normative Disclosure).** No command in this repository goes red when DP-65, DP-66 or DP-67 is violated, and this section claims no coverage for any of them. DP-65 is observable only in a running deployment's queue, and nothing in this repository runs a queue — no service has a startable entry point (ACP-63). DP-66 constrains what future normative text may say and has no runtime shape at all. DP-67 constrains prose in documents this repository does not own. The nearest executable neighbours are the partition suites, and they exercise ledger safety under partition rather than queue capacity; citing them here would be borrowing coverage from a test that checks something else, which is the failure this document's §9 register exists to prevent. All three clauses are recorded there as NOT CHECKED. The check that would change that is a queue-behaviour case asserting that an item over the configured depth bound expires void rather than disappearing, and it does not exist.

**On the unused ids.** DP-68 through DP-70 are deliberately never allocated: three clauses are what can honestly be required, and a range padded to look thorough would be the visible form of the thing DP-66 declines to do.

## 9. Executable Consumers and Conformance Status (Normative Disclosure)

**Most of this document is not checked by anything, and that is the accurate result rather than a gap to be papered over.** Nothing in this repository boots: every service `main()` under `services/` exits non-zero by construction so a scaffold cannot be mistaken for a running control plane, and the only system that actually runs end to end is the Python reference plus `sim.supervise`, which is real OS processes over stdio pipes. A deployment specification describes network segmentation, credential domains, boot ordering, dependency loss and substrate guarantees — none of which is observable from a repository that ships no deployment. So the register below has a **NOT CHECKED** majority, and it says so in the first paragraph rather than in a footnote after the table.

This matters more here than the honesty is worth on its own. The recurring defect this repository has published corrections for three times in one day is **normative text with no executable consumer** — a schema describing an artifact nobody builds (ACP-50), the audit chain formula (AU-1) disagreeing with the reference so per-anchor independent verifiability (AU-3a) could not hold (ACP-57), and one clause id (`CL-7`) naming two different normative rules while both meanings were cited (ACP-56). A deployment specification is the most exposed document this project could write, because so little of it can be executed. The countermeasure is not to manufacture coverage. It is to name, per clause group, the command that goes red — or to say plainly that none does, and to name the check that would.

- **DP-71 (Normative). This document MUST carry a complete executable-consumer register, and a clause absent from it MUST be read as NOT CHECKED.** Every normative clause in this document, this section's own included, **MUST** appear in the register below inside a named range, and every row **MUST** carry exactly one status. Where a check covers only part of a range, the range **MUST** be split into rows and each row **MUST** carry its own status; a single row taking the stronger of two statuses publishes coverage the weaker half does not have.

  *Rationale.* The register is the only place a reader can learn that a MUST in §6 is enforced by nothing. Without it the document reads uniformly normative, and normative text that reads enforced while being unenforced is precisely how the audit-chain (AU-1) and duplicate-clause-id (`CL-7`) corrections survived a full release cycle each.

  *Positive-path obligation, not a control, and the difference is stated rather than dressed up.* The absent-⇒-NOT-CHECKED default has **no branch that reads it**. Nothing in this repository enumerates this document's clause ids and diffs them against the table, so omitting a clause produces no red line anywhere; it produces a silently incomplete register. The fail-safe default of an *absent* reversibility class (RV-1, absent ⇒ `IRREVERSIBLE`) had exactly this shape below floor-HIGH for four releases until the below-floor notice requirement (DR-13) gave it a reader, and the repository publishes that as a lesson. Stating the same shape here without the same admission would be worse. **The check that would close it** is a `tools/selftest.sh` assertion that every `- **DP-N.**` bullet defined in this file appears inside a range named in the register, proven non-vacuously by deleting one row and requiring the assertion to name the orphaned id. **That check is not shipped.** Until it is, DP-71 is an obligation on the author, discharged by review, and it is entered in the register as NOT CHECKED against itself.

- **DP-72 (Normative). The register's status vocabulary is exactly three values, and CHECKED MUST name the command and where it runs.** The permitted values are:

  - **CHECKED** — a command exists in this repository today and goes red when the obligation is violated. The row **MUST** name that command, and **MUST** record whether it runs in the per-commit gate `./tools/verify.sh --suites` or only in `./tools/selftest.sh`.
  - **SHIPPED-WITH** — a check landing in the same commit as this document. The row **MUST** name it, and DP-73 applies.
  - **NOT CHECKED** — no command in this repository goes red. The row **MUST** name the check that would catch a violation, or state that no check in any repository could and why.

  *Why the location is part of the status.* `./tools/selftest.sh` is not the per-commit gate and does not behave like it. Its Rust block runs `cargo test --workspace` and **skips entirely, with a yellow notice, when cargo is absent** — so a claim resting on a Rust unit test is a claim about a machine with a Rust toolchain, not about every green run. Recording only "CHECKED" for the custody tests would overstate them by exactly that skip, and an overstated status in a disclosure section is a worse defect than an honest NOT CHECKED, because it is published as evidence.

  *What NOT CHECKED does not mean.* It does not mean the obligation is optional. A MUST is a MUST whether or not a command watches it; the status column reports the strength of the *evidence*, never the strength of the requirement.

- **DP-73 (Normative). Every SHIPPED-WITH check MUST be proven by a manufactured violation, and the proof MUST target this document rather than a neighbouring artifact.** A check introduced with this document **MUST** be accompanied by an assertion that deliberately breaks the thing it watches and requires the check to *name* the break. A check that has only ever been observed passing is not evidence that it can fail.

  *Rationale, and the trap this clause exists to close.* The clause-id uniqueness assertion in `tools/selftest.sh` already does this correctly: it appends `- **CL-6.**` to a *copy* of `spec/ACP-SPEC-001.md` and requires the detector to return exactly `CL-6`, because a detector whose regex matched nothing would print the same green line as a clean document. Widening that scan to cover this file while leaving the sabotage pointed at a copy of the specification would reproduce the defect one register up — a check introduced to cover a new artifact, asserted by a probe that never touches it. The sabotage **MUST** therefore be moved into a copy of this document, where it additionally exercises the *cross-document* direction, which has no coverage at all today.

  *The mutants the shipped checks kill.* Restore the uniqueness scan to a single literal path and a `DP-` id colliding with a live clause in ACP-SPEC-001 ships green — the duplicate-clause-id defect (`CL-7`) recurring in the machinery built to prevent it. Delete the dangling-citation assertion and a countermeasure column can promise a control that is defined nowhere, which is the state `ES-6` is in today. Delete the no-profile-field assertion over `spec/schemas/bundle/*.schema.json` and add a `profile` property, and a verifier acquires something to read: a deployment's self-declared profile is a derived security value taken from the party under verification, which is the class that recurs along C2 → X1 → Y1 → Z3 → W1 and again in the v1.3.15 quorum-threshold defect. **That assertion is the branch that reads §3's out-of-band default**, and it is the only reason that default is a control rather than a paragraph.   *Why this is not pedantry.* The confirmation gap is not evenly distributed. §14 suite 11's uncovered surfaces include anchoring operations, which is the surface AU-7 sits on — so the clause whose ordering property §6 and §7 of this document lean on hardest is inside the region no qualified outside party has reviewed. Presenting anchor-before-release as settled operational practice would overstate what the specification claims for it.

- **DP-75 (Normative). This document MUST publish no count and MUST copy no limit.** No clause here restates a number that is defined elsewhere — not a suite count, not an assertion count, not a covered-file count, not a latency bound, a hold window, a receipt validity, a skew allowance, a re-drive maximum or a sampling rate.   *Rationale, with the evidence.* `tools/sync-counts.sh` re-derives every published count, and it derives **nothing** from `spec/` and writes **nothing** to `spec/` — a number published in this file is therefore reconciled by no tool and rots on its own schedule. Two unasserted counts have already done exactly that and both are live in the tree as this is written: `dossier/00-INDEX.md:52` says "the proofs, all 14 suites and the external-corpus harness", and `deploy/docker-compose.yml:82` says "proofs + 13 suites".   *A second-order warning about the same script.* `tools/sync-counts.sh:28` states that it will not touch "anything under `spec/` or `dossier/`". The `spec/` half is true and is what this clause relies on. The `dossier/` half is false — the script writes to files under `dossier/` through several sync calls. A comment is not a control, and the one comment this clause cites is half wrong; that is the reason the clause cites the script's *behaviour* rather than its header.

- **DP-76 (Normative). A NOT CHECKED row MUST NOT be promoted by widening what counts as a check.** A row moves to CHECKED only when a named command goes red on a violation of *that* obligation. It **MUST NOT** be promoted by citing a command that exercises adjacent behaviour, by citing agreement between two implementations, by citing a schema validation that cannot express the constraint, or by relaxing the obligation until an existing command happens to cover it.

  *Rationale.* This is the repository's standing rule about instruments, applied to its own disclosure section: raising a floor, loosening a policy or narrowing a corpus until a finding disappears proves only that the instrument is adjustable. The status column is an instrument. The specification's own evidence for why the adjacent-command form fails is the suite-ordering defect (CR-4): the wrong rank table was implemented identically in two languages and asserted by a passing differential, and **agreement between implementations is evidence about consistency and never about correctness**. Pairwise-distinct attester keys (PB-7) is the evidence for the schema form: the specification states outright that the constraint is not expressible in JSON Schema and that validating the registry by schema alone is non-conformant however cleanly it validates.

  *What this costs, stated plainly.* It guarantees that the register stays mostly red for the life of this document, and that adding sections to it makes the ratio worse rather than better. That is the correct behaviour for a disclosure whose subject is a control plane nobody in this repository can boot.

## 10. Residual Risk and Open Problems

The limits come before the claims here, as they do in the specification's Security Considerations (ACP-SPEC-001 §15) and in `dossier/06-RESIDUAL-RISK.md`. Two things separate this section from those, and both are weaknesses rather than strengths.

First, **these are residuals of a document, not of a running system.** Nothing specified here boots: no service in this repository has a startable entry point, and every Rust `main()` exits non-zero by design, so a deployment residual cannot be demonstrated the way a ledger residual can be demonstrated by running the partition suites. The residuals below were found by reading, and reading is the method that found the three corrections ACP-SPEC-001 §1 publishes.

Second, and worse, **no command in this repository goes red if any clause in this section is violated.** §9 records that per clause group rather than leaving it to be inferred, and each clause below repeats it in its own terms. This is not an aside. A deployment specification is the artifact most exposed to the defect ACP-SPEC-001 §1 records recurring three times in one day — normative text with no executable consumer — precisely because so little of it is executable, and a residual section that implied coverage it does not have would be a fourth instance rather than a disclosure of the first three.

Residuals carry `DP-` ids so that `spec/vectors/OBLIGATIONS.md` can key per-implementation obligations to them. An unlabelled limit cannot be cited, and an uncited limit is one a conformance claim can quietly step over.

- **DP-77. Residuals in this document carry `DP-` ids and MUST NOT be numbered into the `RES-` family.** The `RES-` family is defined in ACP-SPEC-001 §15 and currently runs RES-0 through RES-10. Minting RES-11 from this file would put one family's definitions in two documents, which is the collision the whole id allocation for this document was arranged to avoid: the consumption ledger's `CL-7` named two different normative rules for a release, and the correction published in v1.3.15 records why that was unfalsifiable rather than merely untidy — an implementation could satisfy either rule and cite the clause honestly.

  *This is a repository pattern, not a new rule.* `dossier/06-RESIDUAL-RISK.md` already numbers the residuals introduced by the polyglot restructure as RES-P1 through RES-P6 rather than extending §15's sequence from outside the specification. That precedent is followed here for the same reason and stated so a future document does not rediscover it.

  *What breaks without it.* A citation of "RES-11" resolves to whichever document the reader has open. Per-implementation obligations key to clause ids; an obligation keyed to an id with two definitions binds nobody, which is the same unfalsifiability the consumption ledger's renumbering closed one register down.

  *Not checked, and note which half is uncheckable.* The clause-id uniqueness assertion in `tools/selftest.sh` reads one hardcoded path. §9 names the widening this document ships with, and a widened detector would catch a `DP-` id defined twice or a `DP-` id colliding with one in ACP-SPEC-001. It would not catch a violation of *this* clause, because an id minted here as `RES-11` is defined exactly once across both files and is therefore not a duplicate. The rule is enforced by reading only.

- **DP-78. The trust-domain topology of §2 is asserted and not observed, and this document inherits that unmet obligation rather than discharging it.** Nothing in this repository reads a network policy, a credential domain, a firewall rule or a hardware boundary. Tenant separation (D-1), the model path's absence of a route to the Executor segment, the Context Store, the Consumption Ledger and the audit database (D-2), and Bundle Repository isolation from the Policy Engine host (D-3, per §9.1.1 step 3) are obligations on a substrate this repository cannot audit. D-2 already says "Enforced by network policy, verified by test". **That test does not exist**, and it did not exist before this document was written; §2 states its clauses as obligations on a deployment and marks none of them verified.

  *The artifact this document replaces made the opposite impression, which is why the point is stated first.* The deployment topology was previously carried by a diagram at `docs/private/acp-deployment-architecture.html`, which draws six trust boundaries as dashed rectangles, labels the control plane an "isolated segment" and the offline domain "air-gapped · no network, ever", and draws the effect domain with "no route in but a verified Decision Receipt (B-4)". Two things about that file, in the order that matters. It is gitignored, so it is outside the signer, outside the published-count derivation and outside the clause-id assertion — a normative artifact outside the signed roots is not normative. And "air-gapped" is a stronger claim than anything the specification makes: offline bundle-key custody (PB-1) requires an offline key held by the security-policy role, which is not the same requirement as a physically air-gapped host. A drawing cannot be run, so neither divergence could be caught by anything.

  *What breaks without it.* Read as verified topology, §2 would let a deployment that routes the model path to the Consumption Ledger satisfy every clause of this document and pass every gate in this repository, because no gate looks. The isolation is real or it is not, and this repository's evidence is silent either way.

  *Partial coverage, bounded precisely.* §9 names one assertion this document ships with, over `deploy/docker-compose.yml`, which nothing reads today — `tools/selftest.sh` mentions that file only inside a comment. Even once it lands it observes the **demonstrator's** compose topology: it is a real control over an artifact this repository ships and no evidence at all about a customer's network. Reporting it as evidence about a deployment would be the failure mode this project publishes corrections about.

- **DP-79. A deployment profile is only as strong as the verifier's out-of-band configuration, and nothing verifies that a deployment configured its verifier correctly.** §3 requires the profile to be established out-of-band at the verifier and never claimed in the bundle or in any message, because a profile read from the party under verification is a derived security value taken from that party — the class that has recurred through the document's history and is stated generally as the recompute rule (TR-8). Refusing the self-declared form is the right mechanism and it is not a free one: **it relocates trust from the signed bundle to the deployment process, and does not eliminate it.**

  *Where the boundary already is in code.* `TrustedKeys` in `crates/acp-crypto/src/custody.rs` is the shape §3 requires: keyed by fingerprint rather than by a name an attacker controls in the message, no parser and no deserialiser, and `None` for a key it was never configured with — a refusal, not "unknown, assume something reasonable", which is the deny-by-default rule (P-4) applied to custody. What that type cannot do, and no type can, is decide whether the fingerprint it was configured with is the right one.

  *What breaks without it.* A deployment can satisfy every clause of §3 and have configured its verifier to expect a key an attacker holds, or a custody floor lower than the profile it believes it is running. No test in this repository or any other could catch that, because the correct expectation is not a property of any artifact either party ships. This is the limit of the whole mechanism and it is stated as a limit rather than left for a reader to infer from the absence of a check.

  *Not checked, and the two halves differ.* The mechanism half is checkable and §9 names the assertion: no schema under `spec/schemas/bundle/` may declare a profile field, so a verifier has nothing to read even if one were tempted. The configuration half is not checkable and is not becoming checkable.

- **DP-80. Profiles naming custody tier T2 or custody tier T3 cannot be operated by any current build, are aspirational today, and MUST be marked as such in §3's profile table and not only here.** The custody ladder is implemented in `crates/acp-crypto/src/custody.rs` and only its lower half exists. Custody tier T0 keeps its key for the process lifetime and refuses to sign for production, so the higher tiers cannot be bypassed by picking the cheapest key that produces a signature anyone honours. Custody tier T1 may sign for production and its key is wiped at the end of one signature; a second call is `CustodyError::KeyConsumed`, never a silent re-use — which also means custody tier T1 cannot serve a continuously signing online path at all. Custody tiers T2 and T3 are declared and not implemented: the `kms` and `hsm` cargo features are empty, no backend exists anywhere in the workspace, and `OfflineSigner::new` refuses both tiers unconditionally even in a build with the feature enabled, returning `CustodyError::TierUnavailable` rather than downgrading. Naming a tier is not implementing it, and the refusal is what keeps the tier table a control instead of a description.

  *Why the marking has to live in the profile table.* A limit disclosed only in a residual section is one a reader of §3 never meets, and the reader who most needs it is the one costing out a profile. This clause is therefore an obligation on §3's presentation as well as a disclosure here.

  *The label ambiguity, and it is dangerous in the relaxing direction.* Custody tiers share four labels — T0, T1, T2, T3 — with resource floor tiers (RK-1: public/sandbox, internal, production, privileged) and share nothing else. `spec/schemas/bundle/manifest.schema.json` draws the values from `floors.schema.json` so that one ladder of labels has one definition, and says plainly that the two uses share a scale and not a subject. Every occurrence in this document names the ladder, because a bare "T2" will be read as a resource floor — that is what every other clause in the specification means by a tier — and the misreading runs toward believing a control is satisfied.

  *What breaks without it.* A deployment sizes a regulated profile around an HSM-backed signing path, and discovers at provisioning time that no such path exists in this build. A reader who infers that a feature flag turns it on discovers the same thing later and with more confidence, which is worse.

  *Checked in one direction only, and not by the gate.* `cargo test --workspace` runs the custody tests that assert the refusals — the verifier does not learn the tier from the signer, an unconfigured key has no tier and meets no floor, a floor refuses a weaker tier. Those run from `tools/selftest.sh`, **not** from the per-commit gate `./tools/verify.sh --suites`, and selftest skips the whole cargo block with a notice when cargo is absent. They check that the code refuses. Nothing checks that this document's text says so, and nothing checks that §3's table carries the marking this clause requires.

- **DP-81. Notifier self-certification (T-32) is OPEN, and nothing in this document moves it.** The Executor reads `note.source_path`, `note.from_canonical` and `delivered` from the notification service, and consumes all three as evidence *about that service*. They are classified **T** — trusted as transmitted from the party under verification — in `dossier/02b-CLASSIFICATION-TABLE.md`, and the claimed relation between the notification and an independent render path (R12 there) is recorded as undischarged at run time. A compromised notifier that renders through the approval path, labels itself otherwise and reports full delivery passes every independence check (DR-2) and every delivery check (DR-8).

  *Stated at full strength, because the compression is the failure mode.* Splitting `services/notifier` and `services/approval` into separate codebases with separate dependency trees and separate builds improves **build-time** provenance, which R12 already credited. It does **not** move those three rows off **T**, because at run time the Executor still reads all three from the party it is verifying. Closing T-32 means the Executor establishing independence from **two distinct signed service identities named in the signed bundle** — values the notifier does not mint. Anything short of that is a better argument about the build, not a check at the boundary that matters.

  *What this document does and does not contribute.* Drawing the notification path in its own trust domain (§2) is a picture of the intended property, not evidence of it, and a deployment profile (§3) cannot supply the missing identities because a profile is verifier-side configuration and the three rows are runtime inputs. What this document does avoid is adding a fourth **T**: §3's out-of-band shape was chosen so that no profile value is ever transmitted and therefore no profile row enters a deployment's classification table as **T** at all. Under the field-and-relation rule that any unlisted **T** is a conformance failure, the three rows above **MUST** remain enumerated in a deployment's re-derived table; nothing here removes them, and this section must not be read as though it had.

  *Count it once.* `dossier/06-RESIDUAL-RISK.md` records this as the **sixth** recurrence of the recompute rule's defect class, in machinery a fix introduced. That number is not inflated here.

  *Not checked here.* `reference/suites/class_findings.py` reproduces T-32 against the Python reference, which is a check on that implementation's classification, not on this document's disclosure of it. No command reads the paragraph above, and a compressed restatement of it elsewhere would go unnoticed.

- **DP-82. Three problems are open, unanalysed, and recorded rather than answered.** Each is dispositioned in the Annex C voice, and none is resolved by picking an answer here — inventing a rule on top of an unanalysed interaction is new normative work wearing the costume of deployment guidance.

  - **Queue overflow policy.** The attestation queue is partitioned by floor-only risk and its depth is monitored, with depth beyond a configured bound required to be a critical alert rather than a silent backlog (AQ-1, AQ-3). No clause anywhere states what happens *at* the bound. Annex C carries the reason this document does not fill the gap: the interaction between cap-escalated rate limiting and floor-HIGH queue priority is recorded as **Open. Not yet analysed** (X2), and §15's open problems repeat it. §8 of this document therefore states the one obligation that is safe to state and refuses to invent an overflow policy. Two things make the refusal deliberate rather than lazy. Any drop, shed or spill policy deletes items from the one channel queue-depth monitoring watches, so the control disappears while its alert stays green — retuning the instrument that would have found the problem. And **any shedding or priority rule in a multi-tenant deployment couples tenants through one queue**: a tenant able to trip fail-closed controls would influence another tenant's attestation latency, and through the induced-flood composition (RES-2), another tenant's effective risk grade. **Open.** That coupling is raised here for the first time and **this document has not analysed it.**
  - **Monotonic versus wall-clock measurement of the deferred-release hold.** The hold window (DR-1) is a duration; receipt expiry is an instant, and the Executor enforces the window's *length* rather than reading it from the receipt (§9.3 step 5, L-14). The specification names no time source for measuring the hold: the word "monotonic" **never names a time source anywhere in it** — every occurrence is about bundle epochs, audit sequence numbers, the ledger, or the risk-monotonicity lemmas of Annex B. A wall-clock step during the hold therefore either releases early, violating DR-1, or expires the receipt mid-hold — which is exactly the failure the hold-versus-validity rule (DR-6) records as having been found by testing rather than by reasoning. Clock discipline (A-2, §12.5) bounds *skew between components*; it does not make one component's duration measurement monotonic. **Open.** Not analysed here, and deliberately not fixed here: the fix is a change to deferred release in ACP-SPEC-001 §9.6, not deployment guidance, and writing it in this document would put a second definition of the hold in a second file.
  - **Where the Executor's shared epoch mark lives.** §9.3 step 4 requires the receipt's `bundle_epoch` to be at least the Executor's last-seen epoch. That phrase occurs exactly once in the specification, and no clause makes the value durable, shared between replicas, or re-established at boot. The consumed-class list (CL-3) scopes its epoch class to the high-water mark the KMS consults under monotonic epoch binding (RAD-3) — the KMS's mark, not the Executor's — while conformance suite 10 already demands no epoch regression under concurrent Executors, so the obligation exists as an executable test with no clause behind it. The two candidate homes are the Consumption Ledger, where the KMS's mark already lives and where sharing per tenant is already required (CL-5), and an Executor-local durable store, which does not survive a second replica. **Open.** Choosing the ledger here would change what CL-3 enumerates and would be a bundle-rollback question (T-15), which is a specification change and not a deployment one. Until it is answered, cold start and boot recovery (§6) has no clause that makes the mark survive a restart, and §9 labels every §6 clause NOT CHECKED for that reason.

**What would catch a violation of any clause in this section.** Nothing. DP-77 through DP-82 are disclosures, and no command in this repository reads them; the checks named above cover the code and the schemas those clauses describe, never the description. A residual that no command can contradict is a claim about the authors' attention rather than about the system, and it decays the moment the artifact it describes moves. The one structural protection is the id: an obligation keyed to `DP-79` in `spec/vectors/OBLIGATIONS.md` can at least be looked up and found missing.

## 11. Flow Legs and Receiving Obligations (Normative)

Sections 2 through 8 specify domains, the components assigned to them, the
credentials they hold and the stores they depend on. They do not specify the
**wire between them**: what crosses each boundary, and what the receiving
component is obliged to do before it acts. This section adds that, and adds
nothing else — every requirement a receiver applies belongs to ACP-SPEC-001 and
is cited here rather than reproduced (**DP-3**).

- **DP-83 (NEW — Normative). Every crossing of a domain boundary is a leg, and the deployment record enumerates them.** The deployment record **MUST** enumerate, as a **leg**, every crossing of a boundary between two of the seven domains (**DP-5**), and **MUST** give each leg a stable identifier naming its source component, its destination component, and the artifact carried. Identifiers **MUST** be retired rather than reused when a leg is removed.

  *Why enumeration rather than a diagram.* Absence is legible in a list and invisible in a picture, which is the argument §2 already makes for replacing one with the other, restated one layer down. The artifact this document replaced drew seven flows and labelled one of them "the only inbound door" — a claim its own edges falsified, because attestation objects reached the **KMS** and acknowledgements reached the **Executor** across the same boundary, and the time source crossed it without being drawn at all. **DP-7** records that correction. This clause is what prevents the next one: a crossing that has no row cannot be miscounted, because it was never counted.

  *Why identifiers are retired and not reused.* Alerts, runbooks and incident records outlive the document that named the leg. A reused identifier silently redirects a reader from the crossing they are investigating to a different one.

- **DP-84 (NEW — Normative). Each leg cites the receiving obligation by clause id and does not restate it.** For each leg, the record **MUST** cite, by ACP-SPEC-001 clause id, every requirement the **receiving** component applies before acting on the artifact, and **MUST NOT** paraphrase those requirements in its own words.

  *This is **DP-3** applied to the wire, and it is where paraphrase is most tempting.* A leg table invites a plain-language summary of what the receiver checks, because a bare clause id reads as unhelpful. That summary is a second description of a requirement that already has one, and by the third document the mapping back is a reader's inference. The audit chain (**AU-1**) and bundle signature (**PB-8**) corrections are both instances of that failure inside the normative source itself.

- **DP-85 (NEW — Normative). A leg whose receiver applies no obligation is recorded as trusting the channel, and mapped to a disclosed residual.** Where a receiving component applies no verification before acting, the record **MUST** state that explicitly and **MUST** identify the disclosed residual that permits it. A leg carrying no obligation and no such statement is a conformance failure of this document.

  *This is RES-8's rule for the wire, and the omission it closes is the dangerous one.* A leg table listing only the legs that check something reads as complete while describing a subset. Every unchecked crossing is a place where a verifier accepts an artifact from a party on the strength of the channel it arrived on, which is the class ACP-SPEC-001 has hit five times (C2 → X1 → Y1 → Z3 → W1). Suite 12's classification (**§14**) already requires every control **input** to be **R**, **B** or **T** with each **T** disclosed; this clause requires the same discipline of every control **artifact in transit**, which suite 12 does not reach because it classifies inputs at a consumer rather than crossings at a boundary.

- **DP-86 (NEW — Normative). Legs are enumerated for stores, and for components no one has implemented.** The leg register **MUST** include crossings to and from the **Context Store**, the **Bundle Repository**, the **Consumption Ledger** and the **Audit subsystem**, and **MUST** include every component named in **DP-16** irrespective of whether an implementation exists. A component **MUST NOT** be absent from the register on the grounds that it is unbuilt.

  *Why unbuilt components still get rows, and the failure is an enumeration failure.* A component missing because nobody built it is indistinguishable, in a register, from a component that carries no traffic. The distinction matters exactly when planning: the **Context Store** is read at evaluation-order steps 4 through 6 and again at **§9.3 step 9**, and a plan that enumerates services and omits stores will schedule the decision path without scheduling the thing it reads. ACP-SPEC-001 records the same shape one register down as **T-33** — the quorum threshold was an *unenumerated* **T**, and the method could not classify a row nobody had listed. The failure was of enumeration, not of classification.

- **DP-87 (NEW — Normative). A cited clause resolves to a named enforcement mechanism, or is labelled a positive-path obligation with its proof named.** Every clause cited under **DP-84** **MUST** resolve to a named mechanism that refuses when the obligation is unmet. Where the obligation is an ordering or structural property that no refusal can express, the record **MUST** label it a **positive-path obligation** and **MUST** name the test that establishes it. A citation resolving to neither **MUST** be treated as a defect in the record.

  *What this clause is for, stated as the failure it catches.* A clause id resolving in ACP-SPEC-001 proves only that someone **wrote** the rule. It says nothing about whether anything **applies** it, and a receiver obligation that reads as a control and is a sentence is worse than an absent one, because it is published as evidence. This is the same requirement §14's mutation discipline places on a control — a check that kills no mutant is not a control — moved from the implementation to the description of it.

  *The positive-path escape is narrow, deliberately.* Check-then-mutate ledger ordering (**CL-7**) is the worked example: deleting it raises nothing, because the failure is silent corruption rather than a refusal. Labelling it and naming the partition test that proves adoption after heal is a disclosure. Labelling an obligation nobody tested is the abuse this sentence exists to forbid, and the difference is whether the named proof exists and fails when broken.

- **DP-88 (NEW — Normative). The leg register is not a control input.** No component **MAY** weight any decision on the leg register, and no verifier **MAY** read a leg identifier, a cited clause, or an obligation status out of it at runtime.

  *The posture is **DP-5**'s, for the same reason, and it is stated separately because the temptation here is stronger.* The record enumerates exactly the checks a verifier performs, so a verifier consulting it to decide what to check would be reading its own obligations from a document the deploying party writes. That is the fifth-recurrence shape, in machinery written to describe the boundary. **If a future revision gives a runtime component a reason to read this register, that revision has introduced the recurrence.**

**What this section does not do.** It does not specify a transport, a serialization, an ordering between legs, or a retry policy; **§12.2** governs transport and **DS-\*** governs delivery. It does not require a leg to exist — the topology decides that, not this document. And it does not make the leg register evidence that a deployment behaves as the register says: like every other obligation in this document, it constrains an artifact written by the deploying party, and an assessor reading it is reading a claim.
